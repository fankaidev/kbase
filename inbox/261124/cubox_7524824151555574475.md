****![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_png%2FcNFA8C0uVPuQzlZAjS66ZEYbDkdc0DAaC7AvbxPrUmFpdQ5eozPic4tSVCN0YvwfgRX5AIqSHKx8mic2s2a0DjoQ%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D1)****


刚刚，Anthropic 发布了 Claude Ship，将 AI Agent 的工作范围进一步延伸到 GitHub PR 的完整交付流程。

从代码审查、自动修复 CI 失败，到处理合并冲突和审批 PR，Claude 开始参与一项代码从提交到合并的完整工程流程。

这次发布有一个明显的架构变化：Anthropic 没有让单个 Agent 包揽所有工作，而是将 Code Review、PR Steward 和 Claude Approvals 拆成三个独立组件，分别承担审查、修复和审批职责。它们围绕同一个 PR 协作，代码出现问题后可以自动触发修复，修复完成后再进入相应的审查与审批流程。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_png%2FXqAicMdcoiafM1aZ3A7yicTKLHX8IGA4X0Z6Enr4VqDtqAtDI0kWfl1XkYTHWEU818SvCAJNXTYDRo9G3OkVVUEr11OhiaJVxzdiamicjbc8ZFwYQ%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D3)

其中，Claude Ship 引入的策略驱动审批机制改变了 AI 参与代码交付的方式。团队可以通过 YAML 文件定义代码路径、变更范围、审查结果与审批要求之间的关系，系统根据实际修改动态判断审批条件。Agent 能够执行哪些操作，也因此有了明确的规则边界。

这套架构涉及一个更深层的工程问题：当 AI 开始自主修改代码，甚至参与决定代码能否合并，如何避免执行、审查和审批集中在同一个 Agent 手中？Claude Ship 将职责隔离与策略引擎结合，给出了自己的实现路径。


![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_gif%2FXqAicMdcoiafNFib0ukl70HppZqbrZCrCt5JdYhZr4r3QgsB17RrRolWlcoPtrzH4aVpka2vUILoPqLesCRQO95Smhg7avHCIVWKic9Bke8mT4M%2F640%3Ffrom%3Dappmsg%23imgIndex%3D4)

**01**


**PR 成为 Agent 协作的公共状态层**


Claude Ship 将 GitHub PR 作为三个组件共享的工作对象。Diff、Commit、CI 检查、审查线程和审批结果保留在 PR 中，各个 Agent 根据这些工程状态开展工作，并将执行结果写回。这样，任务上下文不再依赖对话传递，代码版本和操作记录本身就能承接后续任务。

工作流由 PR 事件推动。PR 创建、分支 Push、检查失败以及新增审查意见，都会影响后续执行。团队可以选择 Quick、Standard、Deep 三种审查级别，并设置在 PR 创建时、每次 Push 后或人工请求时运行。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_png%2FXqAicMdcoiafOkWXBUg0BGz1fIZicBjQRgv5ib3AyhgtX3AMnQ9V5Ip2BzcGY9v5z7SZXa9V74dMo7mKj2799AvJCyHKpk6anhIN7ISqrEoSG7g%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D5)

Code Review 内部采用 Find、Verify、Rank 和 Post 四阶段处理。Find 阶段由多个 Agent 并行阅读 Diff 及周边代码，从逻辑错误、安全缺陷和边界条件等角度寻找问题。审查范围延伸到修改行之外，因为局部代码能否正常运行，往往取决于调用方、数据流和接口约束。

Verify 阶段负责重新检查候选发现，确认问题能否从实际代码路径中得到支持，Rank 阶段进行去重和严重程度排序，Post 阶段将结果写入 PR，形成行内审查意见和 Check。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_png%2FXqAicMdcoiafPOJpm3HonDxnJh9kvemQhTvraKnHgZv00TOjT3dMZnVdiakmmAUSibPoqchYhgQdR3pljiavYlS9MCX65Xqcj9CvIx3Y03LwjTOk%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D6)

这种设计解决了代码审查中的一个典型问题：模型可以发现可疑代码，却未必能判断它是否构成真实缺陷。独立验证能够过滤一部分缺乏上下文依据的判断。需要注意，Code Review 采用只读方式检查代码，不负责构建和运行项目，因此仍然需要 CI 提供实际执行结果。

PR Steward 则运行在云端会话中，处理与当前 PR 有关的 CI 失败、合并冲突和审查反馈。它能够修改文件、推送 Commit，并说明每次修改的内容和撤销方法。对于范围明确的代码调整，它可以直接执行，涉及较大的架构取舍时，则会等待开发者决定。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_png%2FXqAicMdcoiafMz2h171KUhTfU3CWQ1Cq12pZTCAQZOfqfDBZjgXZJgtl516ichPtfPnth2bOQrS1Q9CMVMaSHg6faibzJictsbeHpgYQO8hyp8Ow%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D7)

它还有明确的触发限制：来自 Fork、Bot 创建，以及提交者没有仓库写权限的 PR 默认会被跳过。运行期间，开发者可以通过 @claude 调整任务，或发送 @claude stop 终止执行。

这里的架构边界很重要：PR Steward 可以写入代码，却没有批准和合并权限。它负责产出新的代码版本，后续审批由独立机制处理。修复和授权被拆开，避免执行任务的 Agent 同时成为自己的验收者。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_gif%2FXqAicMdcoiafOqFZfIntOqicGlzmAonfAgYJYadibAg16q0JUne5VsibQvjWRWuVicjs7881iaMUMb386IsNv5fw4egomJVcA7ic2QXynzcWBbW1940%2F640%3Fwx_fmt%3Dgif%26from%3Dappmsg%23imgIndex%3D8)


![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_gif%2FXqAicMdcoiafNFib0ukl70HppZqbrZCrCt5JdYhZr4r3QgsB17RrRolWlcoPtrzH4aVpka2vUILoPqLesCRQO95Smhg7avHCIVWKic9Bke8mT4M%2F640%3Ffrom%3Dappmsg%23imgIndex%3D4)

**02**


**把仓库规范编译成审批策略**


Claude Approvals 的核心是仓库中的 .claude/approvals.yml。团队将审批要求写成结构化规则，系统根据 PR 修改的文件匹配规则，再计算 Claude 是否可以批准，以及需要多少人工审批席位。

每条 Rule 主要由 paths、if、verdict 和 override 组成。

paths 指定规则覆盖的文件范围，if 描述规则成立的条件，verdict 决定审批结果。其中，claude 有 approves、comments 和 blocks 三种状态，分别表示允许 Claude 批准、只允许留下审查意见，以及阻止审批。seats 则规定人工审批人数，还可以限定参与者来自哪个 GitHub Team，或排除 PR 作者。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_png%2FXqAicMdcoiafPtWlP0cXB4OLTRrN3nHH69iahZ8yBl4mOvP4gYIG3xgKlcZCbQuk5oAST51cbOfbSJJyvic2mmvqYNtUF2jhIyCEibg1lawj7Vico%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D10)

这套规则采用逐文件评估。系统会检查每个修改文件适用哪些 Rule，再将结果汇总到整个 PR。如果同一文件匹配多条规则，会保留约束更严格的结果，优先级依次为 blocks、comments 和 approves。不同规则要求的人工审批席位也需要分别满足。

目录级配置进一步解决了大型仓库的规则维护问题。系统会从变更文件所在目录向上查找策略，使用距离文件路径更近、处于 Enforce 状态且覆盖该文件的配置。上层策略可以通过 nested: inherit 继续约束下层目录。组织能够在根目录维护基础规则，业务模块则可以根据自身代码特点设置局部要求。

条件表达式还可以读取 PR 的文件数量、Diff 行数、作者、发起者和目标分支等属性，并支持 ANY、ALL 等逻辑组合。这里有一个细节：pr/diff_lines 统计整份 PR 的变更规模，rule/files_changed 只统计当前规则覆盖的文件。两种统计口径让团队可以同时管理整体修改规模和局部模块的审批要求。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_png%2FXqAicMdcoiafMSbrOjERqibQYpXrwNY8V2ZmEp5ep8Pc5ic0k5Jic3vbDY6BJhjuSvBtqNChWvoNoWnNFIBHiavDnQ6ttiayk7P7CStlBdMlXo45L4%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D11)

override 则允许在基础 Verdict 上增加条件分支，系统按配置顺序采用首条成立的规则。它可以根据审查结果调整人工审批人数，或者改变 Claude 是否拥有批准权限。

这种策略计算需要考虑模型调用失败的情况。如果 Override 依赖的分类器没有返回结果，系统会回到基础 Verdict，如果分类器出现在 Rule 自身的 if 中却没有结果，审批 Check 会失败。因此，基础规则需要保留足够严格的审批要求，避免模型调用异常时意外放宽权限。

还有一项关键的安全设计：Claude Approvals 从默认分支读取策略文件。PR 中尚未合并的审批规则修改不会作用于当前 PR，只有规则进入默认分支后才会参与后续评估。这避免了提交者通过待审查代码修改审批条件，为自己的代码降低门槛。

Claude Approvals 不能直接读取 CI 结果，测试和构建仍然需要作为独立的 GitHub Required Check 运行。它自己的 Check 也需要被配置为 Required Check，才能实际参与合并约束。Observe Mode 则允许团队先运行策略、观察审批结果，再决定是否启用强制检查。


![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_gif%2FXqAicMdcoiafNFib0ukl70HppZqbrZCrCt5JdYhZr4r3QgsB17RrRolWlcoPtrzH4aVpka2vUILoPqLesCRQO95Smhg7avHCIVWKic9Bke8mT4M%2F640%3Ffrom%3Dappmsg%23imgIndex%3D4)

**03**


**让语义判断参与审批**


路径规则和 PR 属性能够描述修改发生在哪里、规模有多大，却无法充分表达代码在语义上发生了什么。Claude Approvals 通过 Classifier 补充这层判断。

团队可以在 .claude/classifiers/ 中创建分类器，通过 def.yml 定义模型、Prompt、输入参数和输出范围。Prompt 负责描述判断任务，outputs 则限制模型可以返回的结果，例如 low、medium 和 high。策略引擎读取这些结构化结果，再根据条件决定审批要求。

Anthropic 内置了两个分类器：claude/code_review 和 claude/diff。

前者读取 Code Review 的结果，没有尚未解决的 Important 级别发现时返回 pass，仍有此类问题时返回 fail。后者比较新旧 Diff，将变化归类为 trivial、same_intent 或 different，判断后续代码修改是否延续原来的意图。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_gif%2FXqAicMdcoiafO4BYtuekB4Aul81sytnUxiciaWy604XzR9uCHR9f1uBD62Zciaic8dPI13Ne550zHSibWtxYGZQRcUOJpK6f63cMibyibiaboEib01u8FY%2F640%3Fwx_fmt%3Dgif%26from%3Dappmsg%23imgIndex%3D13)

这里引出了 Claude Approvals 中一项很有技术含量的设计：reuse。PR 每次 Push 后，原有人工审批是否仍然有效，需要结合新版本代码重新判断。如果每次修改都让全部历史审批失效，人工需要反复处理大量局部修复，如果无条件保留旧审批，新代码又可能沿用已经不适用的授权。

reuse 允许团队分别设置人工审批席位和分类器结果的复用条件。例如，只有新旧 Diff 被判断为 same_intent，同时新版本 Code Review 返回 pass，之前的人工审批才继续计入。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_png%2FXqAicMdcoiafNygTppclw2vfbfAsApQM0vh362wDgxdTyxH2J2yF31gyUKyK18l4iaaqwWlMnVwx3OWBwhzfAx39Ndp52TmiaubElyyib5NCLUYc%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D14)

这里实际上有两层判断：claude/diff 检查修改意图是否延续，claude/code_review 检查当前版本是否仍存在重要问题。两个条件结合后，系统才能决定是否保留历史审批。

reuse 还支持通过 max_age 限制评估结果的有效时间，超出时限就需要重新计算。GitHub 已撤销的审批通常不会自动恢复，强制推送也可能影响旧审批的有效性。如果作者曾经填补人工审批席位，复用后这个席位也可能继续计入，因此团队需要通过人员规则排除 pr/authors，避免作者替代独立审批人员。

Classifier 还可以配置工具权限和执行预算。部分分类任务只需要读取 Diff，另一些则可能需要查看周边代码或审查线程。工具列表决定分类器能够访问的内容，预算则限制运行时间和 Token 消耗。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_png%2FXqAicMdcoiafMJrsp0gerribcIZ3FfVfI3uu6MzJ9jWibvNUgp12B4yaxzDCROyASM2Vj1xqlnVnAh22glLhTJN6eW9QXP11jwxM6BsVCKeg0aU%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D15)

审查发现也有独立的权限管理。团队可以通过 findings 规定哪些人员有权关闭分类器产生的发现。这里需要区分关闭审查线程和修复代码：前者只改变问题的处理状态，后者才会改变实际实现。如果缺少人员权限约束，审查状态可能被人为改变，进而影响后续审批。

语义分类还有输入风险。PR 描述和代码文件可能包含干扰模型判断的指令文本，即使输出被限制为固定类别，模型判断仍可能出现偏差。因此，涉及高风险代码的策略仍应保留人工审批，不能仅凭分类器输出降低权限要求。


![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_gif%2FXqAicMdcoiafNFib0ukl70HppZqbrZCrCt5JdYhZr4r3QgsB17RrRolWlcoPtrzH4aVpka2vUILoPqLesCRQO95Smhg7avHCIVWKic9Bke8mT4M%2F640%3Ffrom%3Dappmsg%23imgIndex%3D4)

**04**


**代码交付自动化之后的工程挑战**


Claude Ship 能够缩短代码提交、审查与修复之间的等待时间，但软件交付效率并不完全取决于 PR 的处理速度。

随着 Agent 持续参与代码修改，审查质量、修复范围以及多轮修改产生的累积影响，会成为衡量这套系统的关键因素。尤其在大型项目中，局部代码通过审查，并不意味着整个系统的行为符合设计预期。

审批策略的维护成本同样需要考虑。随着业务模块增加、团队职责调整和代码结构演变，规则之间的继承关系、例外条件和分类标准也需要持续更新。如果自动化节省的时间被策略维护和异常处理消耗，其实际工程收益就需要重新衡量。

因此，评价 Claude Ship 不能只看它能够独立处理多少 PR，还需要观察回滚比例、缺陷遗漏情况、人工介入频率以及整体交付成本。相比单纯提高代码生产速度，如何让这些自动化能力在复杂工程环境中长期稳定运行，或许才是 Anthropic 接下来需要解决的问题。

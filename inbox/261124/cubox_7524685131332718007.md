你有没有想过，再过一年，我们今天在电脑上打开的绝大多数软件，从客户管理系统、报税后台到各种内部审批工具，可能都会失去自己的界面？在大多数创业公司还在拼命往自己的软件里塞一个聊天侧边栏、或者用拖拽流程图拼凑工作流的时候，有人直接给这些做法判了死刑：到了 2027 年，应用层只会剩下一种通用的 Agent 操作系统，其他所有软件都会退化成给这层操作系统供数的数据库。


写出这番话的人叫 John Suh。他不是那种只看财务报表的分析师，而是一个在真实业务和底层代码里都摸爬滚打过的工程师。他本科在普林斯顿先读哲学后转计算机，期间回韩国军队当过情报中士，还去阿联酋给韩国特种部队做过八个月随队翻译。退伍回硅谷后，他在 Robinhood 亲手设计并写出了借记卡充提款系统，这套系统后来每年给公司带来上亿美金的收入。再往后，他自己做过消费级 AI 创业，公司被收购后，他成了全球第一家 AI 控股公司 Long Lake 的创始团队成员和合伙人。


Long Lake 的打法在硅谷非常特别。他们不做软件卖给传统企业，而是直接花大钱把传统服务业公司买下来长期持有，再派自己的工程师进驻进去，用 AI 改造里面最繁琐的真实业务流程。今年他们联合 General Catalyst 和 Alpha Wave，直接掏出 63 亿美金买下了全球最大的企业商旅平台美国运通全球商务旅行（Amex GBT）。最近，John Suh 离开 Long Lake 准备开启自己的新项目，顺手把过去一年在传统大企业里踩过的坑、以及自己亲手写过的五个开源试验项目，浓缩成了四张架构长图，讲清楚了 2027 年的 Agent 平台到底长什么样。这组图发出来当天，就有超过 42 万人围观，近万人收藏。我觉得这组图最难得的地方在于，它不是坐在办公室里想出来的技术畅想，而是把今天市面上大半 AI 软件公司的遮羞布给扯了下来。

**十家会计师事务所审税表，就把垂直 SaaS 的投资逻辑戳破了**


过去十几年，硅谷风险投资最喜欢讲的一个故事叫垂直行业软件（Vertical SaaS）。逻辑听起来很顺：挑一个细分的传统行业，比如会计、律所、物流或者牙医诊所，因为同行干的活都差不多，只要做出一套专门针对这个行业的标准软件，就能卖给全行业的所有公司。到了今天，这套故事摇身一变，成了各个垂直领域的 AI 平台。


可在真实企业里待过的人都知道，这套假设从根子上就有问题。John Suh 举了一个特别扎实的例子：你去看十家不同的会计师事务所怎么审核报税表。在同一个行业里，每家公司嘴上说的词都一模一样，都叫审核某张表格；但你只要坐到那些会计师旁边看半个小时就会发现，每一家评估和理解这张表的方法、先看哪个字段后看哪个字段、遇到异常怎么核对、甚至界面上习惯把哪个框放在左手边，全都千差万别。


结果就是，市面上那些做得最好的垂直行业软件，卖着卖着最后全都变成了极其沉重的定制平台。软件公司不得不养一大批售前工程师、实施顾问和驻场部署团队，每签下一家大客户，就派人过去驻场几个月，帮人家改配置、调界面、接数据。John Suh 的反问非常直接：既然这些会计师事务所理想中的工具，其实是把 Excel 复制一份出来、改成完全贴合自己习惯的专用界面，既然最后反正都要靠人去给每家公司改界面，那企业为什么还要买一个束手束脚的三流行业软件，而不是直接用一套底层的通用 Agent 操作系统？


![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_jpg%2F15Dz37YtAksNaG5SU2DJPmB8xKSxcWSu9ntg41F6mqekloegD3su2f9lHaEVtc40kzsgEiaLneCBJTlkuXhVGZz8P36qetKju7xjulic5NW6U%2F640%3Ffrom%3Dappmsg%23imgIndex%3D4)

在他描绘的 2027 年平台里，软件界面不再是供应商刻在石头上发给你的成品，而是装在云端文件系统里的一个个小应用（Apps，也就是现在大家常说的 Artifacts）。现在很多人把 Replit 这种写代码的工具、Claude 生成的网页小组件、以及嵌入在聊天框里的小卡片当成三类不同的东西，但在他看来，这些最后都会合并成同一种东西。整个平台就像一套出厂自带了默认软件的操作系统，每个用户和每家公司在自己的文件夹里都有一份所有界面代码的副本。会计师觉得审税表的页面不好用，不需要给软件公司的实施顾问提需求排期，直接跟自己的 Agent 说一句，把左边这栏拆开、加一个自动比对去年数据的按钮，Agent 当场就把那个界面的代码改好生效了。


![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_jpg%2F15Dz37YtAkvxGDmIIV71HIiapDLiasxribicEQd7Z8bto05YHSYtlOm3l41G2JzYeWL3b3W5SsndFEJld8xyIKRlZlRpMHW8C1JGjPZ0Lmlq744%2F640%3Ffrom%3Dappmsg%23imgIndex%3D5)

我非常认同这个看法。我们过去需要软件公司，是因为写代码和改界面的成本太高，高到只有把同一套界面卖给一万家公司才能回本，所以企业只能削足适履，去适应软件的脾气。现在 Agent 随时能改写界面，软件迁就人的成本第一次降到了零。这时候谁还在赌全行业共用一套死板的工作流，谁就是在用上一代的惯性做这一代的产品。


**为什么连最鼓吹超级 Agent 的 Anthropic，真干活时也只给它配两个工具**


既然界面和工作流都能让 Agent 随时改写，那底层到底要跑什么样的 Agent 才能撑住这种折腾？这里就碰到了今天 AI 圈子争论最凶的一个问题：未来到底是一个无所不能的超级 Agent 包打天下，还是成百上千个专门的 Agent 协同干活？


表面上看，像 Anthropic 这样的大模型实验室一直在公开场合主张超级 Agent 的路线，觉得模型足够聪明以后，一个 Agent 就能搞定一切。但 John Suh 敏锐地抓住了他们身体比嘴巴诚实的一个细节。前不久，Anthropic 的研究团队做了一个轰动一时的实验，指挥大约一千个 Claude 协同工作，花了二十八个小时，把费马大定理的数学证明翻译成了计算机可以逐行检验的形式化代码。在这个实验里，研究人员给每个 Agent 配了什么装备呢？只有一个命令行终端（Shell）和一个文件编辑器。


你只要设身处地想一想就能明白：哪怕最顶级的模型已经聪明到能分清什么时候该用什么工具，当你作为一个研究员，正在指挥一千个 Agent 去攻克费马大定理的时候，你绝对不会希望这些算数学题的 Agent 身上还挂着你的个人邮箱、网盘和全网搜索插件。万一哪一步跑偏了，把草稿发给了客户，或者去网盘里乱翻一通，麻烦就太大了。所以哪怕在最鼓吹超级 Agent 的公司内部，真到了严肃干活的时候，大家实际用出来的也是用代码把权限和工具卡得死死的专门化配置。


一旦承认一家公司里会跑着各种各样不同配置的 Agent，而且这些 Agent 还会在干活的过程中自己给自己写新的插件、改自己的拦截挂钩甚至调整运行逻辑，现有的底层架构就撑不住了。今天硅谷绝大多数号称能大规模跑 Agent 的团队，底层用的都是像 Temporal 这样的持久化工作流引擎，逻辑是把任务拆成固定的步骤，挂了就从断点重放。但 John Suh 认为，到了 2027 年，底层的标准做法一定会转向独立运行时的模型（Actor 模型，比如 Cloudflare 的 Durable Objects 或者 Vercel 最近开源的 Eve）。


![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_jpg%2F15Dz37YtAksfa190Lfd87arRLCnV3IicEyDGxnOToP97RS3xywk1iaAic4lcqwDNsU5EFY5PiaAJBqSeU1Lvgg70TmL2PZU4TmthH1of025Oo58%2F640%3Ffrom%3Dappmsg%23imgIndex%3D6)

道理也不难懂。如果一个 Agent 只能在预设好的轨道上跑，那大家挤在同一个后台里没问题；可如果一个 Agent 具备自我改进的能力，干着活突然自己写了一段新代码插进自己的运行循环里，你就必须给它一个和别人完全隔绝的独立房间，连带着它自己的贴身小数据库一起锁在里面。只有这样，一家公司底下同时跑着几百个自己改过代码的 Agent，才不会因为其中一个改错了东西，把整个公司的后台全部搞崩。搭配上随时能按快照复制的云端沙盒，一个 Agent 可以瞬间开出五台虚拟机试五种不同的方案，也可以一千个 Agent 并行控制一百台电脑，这才是百万级 Agent 集群该有的底座。


![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_jpg%2F15Dz37YtAksWRUHqqp0OchMyxLGtic7icbZb0Dp2hBHkyXjbibc4thIRekE3QVX71JyO8hsMmVKAIvFWrcArXGHcGpRib9nFibaBkcia0AHHjnb5E%2F640%3Ffrom%3Dappmsg%23imgIndex%3D7)

**把底层执行过程直接甩给用户看，是今天大多数编程工具最大的误区**


有了能自己在后台折腾的 Agent 集群，人该怎么和它们打交道？在这个问题上，John Suh 把今天市面上几乎所有当红的编程 Agent 和开发工具都得罪了一遍。现在绝大多数工具的默认做法，是把 Agent 的底层工作会话（Session），包括它中间调用了哪个工具、读了哪行代码、报错了怎么重试的过程，原封不动地直接铺在屏幕上给用户看。他的评价很干脆：这完全错了。


他的观点是，底层的执行会话和给人看的对话（Conversation）必须彻底分开。人平时打交道的对象，应该是一个和微信群聊、Slack 频道或者邮件往来处在同一个抽象层级的对话窗口。底层那个满屏滚着工具调用日志的会话，它的地位应该跟软件的源代码一样，只是你觉得哪里不对劲、想要掀开机盖去检查和调试系统时才点开看一眼的东西，绝不应该当成日常的主界面。Agent 在后台怎么翻文件、怎么调接口是它自己的事，只有当它决定要跟人说句话的时候，才通过一个专门的发消息动作，把那句话干净地发到人的聊天窗口里。


他甚至预言，这两年冒出来的那批靠把底层编程会话包装一下就拿去卖钱的开发环境（比如 T3 这类工具），很快就会撞上当初 Cursor 面临的那种创新者窘境，而且绝大多数都活不过这次转型。为了验证这个想法，他自己去年到今年先后写了三个开源项目，其中有一个叫 Teraslack，就是做了一个长得像 Slack 一样的工作区，人在里面看到的只是清爽的频道和对话，而背后成群的 Agent 都有各自独立的后台会话，通过接口在频道里跟人汇报和接活。


![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_jpg%2F15Dz37YtAkuQolHRqa7ADUmzeUia5GOWXPueBenNPY6lmiczUNdWyCHSU5tmzPpl5t6aWngc6Yp7F03J0Kz2O8CoM2HSibht8pT9k5S3yMZRsk%2F640%3Ffrom%3Dappmsg%23imgIndex%3D8)

如果再往前推一步，当手底下的 Agent 越来越多，人其实连聊天记录都看不过来了。到时候，人每天打开电脑最常看的地方，会从聊天窗口变成一个专门负责拍板和答疑的收件箱（Inbox）。他在几天前写过一句特别精准的总结：AI 原生的待办事项列表，就是一个审批队列。Agent 能自己干完的活早就悄悄干完了，只有那些超出它能力范围、或者风险太高必须由人来拿主意的最后一步，才会被推到这个收件箱里。而且这个收件箱不是只弹一行冷冰冰的文字通知，它会针对具体的业务带上一个定制好的小界面，让公司里的业务专家能一眼看清前因后果，填上自己的判断或者点下批准。到最后，一个公司的员工每天在这个收件箱里做的每一次批注和拍板，其实就是在顺手给公司自己的模型做强化学习的标注数据。


**推翻自己 64 万浏览的爆款想法后，他发现公司记忆只需要两个文本文档**


读这四张架构图的时候，很多懂行的人第一眼会发现少了两个今天最火的词：一个是公司大脑（Company Brain），一个是长期记忆（Memory）。现在硅谷有大把创业公司拿着这两个词去融了几千万美金，可 John Suh 却在帖子下面专门置顶了一条补充说，他是故意不写这两个词的，因为在他眼里，这两件事根本不难，甚至可以说是已经解决掉的问题。


他敢这么说，是因为他自己就在这件事上摔过一个大跟头。今年六月，他发过一条有 64 万人看过的爆款帖子，当时的设想非常宏大：他觉得未来的公司都得从头重建，把公司里所有的监控日志、产品指标、文件修改、聊天记录和邮件，统统塞进一条按时间顺序只准追加、不准修改的全局大日志里。他不光嘴上说，还真挽起袖子用 Rust 语言加上 Kafka 和 ClickHouse 写了一个完整的开源系统叫 Nanotrace，想把这个终极数据底座做出来。


结果写了几个月，他自己把项目停掉了。在这次和网友的讨论里，他特别坦诚地复盘了当时的钻牛角尖：一家十万人的大公司，难道真的要把十万名员工每天收发的每一封邮件、网盘里的每一次文档改动、日历上的每一个日程变化，全都实时塞进同一张全局事件表里吗？对一家大企业的业务体量来说，这并不算什么核心资产；可对要去读这张表的 Agent 来说，这简直就是能把上下文活活淹死的垃圾数据海。他毫不留情地自嘲说，写完那个项目才意识到，那纯粹是一场被技术执念带偏的过度工程，是典型的 AI 狂热症，既没有必要，也不切实际。


从那个大坑里爬出来之后，他的思路一下子变得极其干净。既然全局大表走不通，那公司大脑和记忆到底该怎么做？答案简单得让人意外：只要底下有一个带权限控制的云端共享文件系统，上面放几个纯文本的 Markdown 文件就够了。具体来说，只需要一个只管往后追加新记录的日志文件（memory_log.md），再加一个记录最新状态的当前文件（memory_current.md），然后让几个后台的值班 Agent（也就是大家说的做梦 Agent，dreaming agents）定期去读一遍日志、更新一下当前状态。至于什么是个人记忆、什么是部门记忆、什么是某个具体客户的记忆，根本不需要设计复杂的数据库表结构，直接在文件系统里建几个不同的文件夹，按目录和单个文件设好谁能看、谁不能看的权限就彻底解决了。比如老板、人事和 Agent 讨论某个员工薪资的记录和生成的文件，锁在只有他们能读的目录里，普通员工的 Agent 根本摸不到。


同样的道理也用在了怎么接外部数据上。现在好多平台都把预置了多少个第三方软件连接器当成卖点，或者指望全世界的软件都按统一的标准发事件。他在评论区直接泼了冷水：指望外部系统主动按新标准发数据，覆盖面连百万分之一都不到；而世界上没有现成接口的内部老旧软件，比有接口的软件多出一百倍。与其等平台官方慢吞吞地做连接器，不如直接让 Agent 随手写一段监听代码（Listeners 和 Monitors）。今天你想让每封进来的邮件都先过一遍筛选再触发任务，明天你想改成只盯着某家客户域名发来的邮件盯一个礼拜，直接跟 Agent 说一声，它当场写个小脚本挂在那里听着就完事了。


我读到他复盘自己放弃 Nanotrace 的那段话时，心里挺感慨的。技术圈里最不缺的就是画大饼的人，一条帖子拿了六十多万浏览，换作别人早就拿着PPT去融一轮大的了；能亲手把代码写出来、发现不对劲又亲手把它推翻，最后退回到几个最朴素的文本文档和文件夹上，这才是真正干过活的工程师才有的诚实。


**我自己的一点思考**


把 John Suh 这四张图和他在评论区里的几十条回复连起来看，他最想让人记住的其实是一个比喻：能赢到最后的 Agent 平台，长相不该像一座全自动的黑灯工厂，而应该像一座花园的底座。


工厂的逻辑是标准的流水线，就像今天的垂直行业软件，或者像 n8n 和早期 Zapier 那种拿鼠标拖拽方块连线的自动化工具，一旦业务稍微超出一丁点预设的格子，整条线就卡住了。而花园底座提供的是土壤、水源和围栏，也就是他说的带细粒度权限的云端共享文件系统、彼此隔离的独立运行时、随时能开关的沙盒电脑，以及让人在最后一步拍板的审批收件箱。有了这块地，每家公司自己去种自己的种子，长出来的树和花，也就是那些用代码写出来的工作流和随时能改的业务界面，自然每一棵都不一样，由着人、Agent 和业务的真实信号一起慢慢修剪和演化。


不过，要让这座花园真正在大企业里长起来，我也有两处放不下心的事。第一处是当普通业务员都能让 Agent 随手改软件界面、随手写监听脚本的时候，一家公司的业务逻辑会不会在几个月里碎成一地没人管得了的补丁。以前会计师事务所虽然嫌软件难用，但至少全所上下用的是同一套死板的标准；如果十个会计师每个人让自己的 Agent 把审税表的界面改成了十个样子，连校验数字的规则都各自改了一套，出了财务事故算谁的，怎么审计，这恐怕不是技术隔离能彻底解决的管理难题。


第二处是他预测说，这层终极的应用层操作系统有很大概率会由一家独立创业公司拿下，而不是落入 ChatGPT 或 Claude 手里。理由是独立公司没有历史包袱，能跑在最前面。但我们也看到，模型实验室自己也在拼命往下做文件系统、沙盒和收件箱，当底层的推理能力和上面的操作系统咬合得越来越紧，留给独立平台公司的窗口期其实非常窄。


即便如此，这套蓝图依然是我今年看过的对未来两三年软件形态最清醒的拆解。下次你再看到哪家公司宣传自己做出了某个垂直行业的专属 AI 软件，或者吹嘘自己有几百个拖拽组件的时候，不妨拿那十家会计师事务所审税表的例子去问问它：如果我的业务员下午想改个界面字段，是得找你的驻场工程师排期，还是跟自己的 Agent 说句话就能办好。能回答好这个问题，大概就能看清谁还能留在 2027 年的牌桌上了。

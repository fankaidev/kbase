"你能多快拿到反馈？多快验证这个想法？"  

"如果你的团队有技术债，那也是你的问题。"  

"先把价值说清楚，再定义能衡量这个价值的指标。"

客户想改个流程，产品经理写好需求、等工程师做出第一版，再把链接发回去，才发现自己一开始就理解错了。Salesforce AI 工程负责人 Jayesh Govindarajan 举这个例子，是想说明原型可以更早拿给客户看，有些分歧在写正式需求之前就能问清。

等 Agent 真要替客户查账、退款，团队还得定下来它该查什么数据、用哪版政策、什么时候交给人工。 Jayesh 带领的约 700 人 AI 工程组织里，有人负责模型，有人让模型接上数据和工具，也有人专门做评测、盯着 Agent 上线后的表现。

## 在客户提出需求的地方做原型

Jayesh 的团队平时用 Slack 讨论工作，也会通过 Slack Connect 和一些客户直接协作。客户为什么提需求、之前试过哪些办法，都可以连着原来的对话一起看。 有时客户看了界面，只想改个按钮，有时看到按钮才发现，两边想的根本是两件事。

"产品经理可以在和客户的 Slack 对话里做个小原型，直接问他：这是你想要的吗？"

Jayesh 说，Salesforce 凭着多年的客户关系，通常能很快找到十家愿意试用的客户。他更在意的是团队能多快把原型交给客户、拿着反馈改下一版。 要是团队平时很少接触用户，工程师的排期缩短了，等着约到客户的时间照样得算进去。

按 Jayesh 的说法，工程师一开始常用 Cursor，后来不少人更愿意用 Claude Code。Salesforce 先让工具过安全审查，再给团队一段时间试用，最后看大家日常做事选了什么。

Jayesh 谈到，产品经理可以在客户的 Slack 对话里做出原型，直接确认需求。

## 产品经理得写得出八分和十分的答案

在 Jayesh 的团队里，产品经理可以先做原型，工程师有想法也可以直接去问客户，但小队的人员配比暂时没太大变化，还是由产品经理、工程负责人、几位工程师和部分时间参与的设计师组成。谁都可以先动手，做成正式产品时，还是得用上各自的专业经验。 产品经理能判断几家客户说法不同的需求能不能归到一个功能里，工程师则要考虑这个功能从一千家客户用到一万家会不会出问题。

主持人 Aakash Gupta 举了个例子，用 100 条输入做一组参考用例，Jayesh 也赞成尽早做这件事。产品经理要给出不合格、八分和十分的回答样例，让工程师换过模型之后还有同一把尺子可用。 以部分退款为例，八分的回答可以查对订单、告诉客户能退多少，十分还得解释为什么只能退这么多、接下来需要确认什么。要是查错了订单、报错了金额，或把没办成的退款说成已经到账，回复再客气也得判不合格。实际门槛由负责退款业务的人定。

"你能不能定个标准，说清楚什么才算做得好？这就能转成评测。"

Jayesh 说，做数据科学的同事习惯在开发前就想好怎么判断结果，工程团队也开始用这个办法。同一个退款用例里，金额和工具调用可以直接和预期值对照，政策解释则要看有没有说清适用哪条规定。

招产品经理时，Jayesh 还看对方能不能主动把事往前推。比如遇到一项反复要做的工作，先自己做一遍，再教 Agent 按这个办法做。接下来还得看得出哪次交付只是看起来像样，能不能把发现的问题写成下次能跑的用例。

## 聊天框能换，数字得从同一个地方来

Aakash 问，如果用同一个口径查待成交商机的总金额，模型一次报 2,500 万，一次报 2,000 万，公司该用哪个数？模型可以理解用户在问哪个地区、哪个时间段，但金额得由业务系统按指定字段查出来，这样才有记录可核对。

Jayesh 说，把 Salesforce 的入口放进 Claude 等工具里，仍可以通过接口使用客户原来配置的数据和业务流程。Salesforce 的 Agent Script 可以写清哪些步骤按规则执行、哪些地方需要模型判断，比如让模型理解客户遇到了什么问题，再按已有的退款规则计算应退金额。

## 换模型之前，先拿旧问题考新模型

Jayesh 举了个假设，一直正常工作的退款 Agent，可能因为有人改了政策文档、把新规则写得含糊，就开始开出超额支票。即使代码一行没动，Agent 读到的资料或背后的模型一变，原来能办对的事也得重新查一遍。

Jayesh 把这些工作叫作智能体开发生命周期，简称 ADLC。上线前，团队跟客户确认任务，做出来、跑用例，再决定能不能交付。上线后如果某类请求开始出错，团队得追到那次调用读了什么资料、执行了什么操作，才能判断应该改政策、补规则，还是让人接手。 Salesforce 提供测试和运行观察工具，Jayesh 提到的 Optimization Agent 还能帮助发现哪里缺资料、哪些提示词需要调整。

有些为旧模型设计的步骤到了新模型上可以简化，但手里如果没有一组能重跑的用例，团队就说不清楚哪些旧问题仍能办对、哪些规则已经被绕过去了。 拿退款来说，可以用同一版政策和同一批订单，让两个模型各跑一遍，逐条查它们选了哪张订单、退了多少钱、该转人工时有没有转，等分清哪些差异是换模型带来的，再试着删减原来的步骤。

写代码快了以后，Jayesh 更在意代码能不能及时审完，测试能不能在上线前发现问题。 他的团队和安全、发布团队一起做辅助代码审查的 Agent，他也建议把发布拆成一批批对客户有用的改动。工程师要是总在修过去留下的问题，能做新功能的时间就少了，所以他把技术债也算在产品经理的账上，排下一轮工作时得一并考虑。

## 客户现场的解法，怎么进产品路线图

Jayesh 认为，产品往哪个大方向走，仍得由团队先作判断，再用两类反馈修正，一类来自客户试用原型，另一类来自客户实际使用已经上线的产品。后者常由直接跟客户做实施的前线部署工程师带回来。现有工具缺了一段，他们可以先找其他工具接上，必要时和客户一起做个定制版本，等流程跑起来，再看这个办法有没有必要做进产品。

前线工程师会把客户卡在哪一步写到专门的 Slack 频道，产品经理和工程负责人对照路线图决定怎么处理。小障碍修掉就能继续用，如果三家客户都在同一个功能上费劲，就值得回现场看看当初是不是把流程想错了。

前线工程师可以把现成的定制版本拿给其他客户试，看这个办法值不值得做进通用产品。 试的时候要问两件事，别家有没有遇到同样的问题，这个版本能不能让他们也把流程跑通。几家都用得上，产品经理和设计师才有依据跟前线工程师一起调整方案。

谈到产品路线图时，Jayesh 把客户试用原型和上线后的实际反馈都列为判断依据。

## 先在一条业务上交出结果

Jayesh 见过一些项目上来就要改造全公司，范围越做越大，做项目和等结果的人都急。他建议挑一件值得解决的事，先把整条流程跑通，开工时就约好拿什么判断它做成了。 以招聘预筛为例，可以看 Agent 有没有问到规定的问题、该转人工时有没有转，再看招聘人员花在初筛上的时间有没有减少。

Jayesh 提到的一家欧洲大型招聘公司先做文字预筛，覆盖 17 种语言，随后再往语音面试推进。 按他的描述，语音 Agent 可以接着候选人前面的回答继续提问，必要时转给人处理，访谈里没有给出节省时间或成本的数字。

## 写在最后

手头如果有个准备上线的 Agent，可以和同事挑一条最常见的请求，再挑一条最怕办错的。把每条请求该查什么、能做什么、出了例外该交给谁写进用例，下次政策变了或模型换了，就拿同样的问题再跑一遍。 这样能看出改动有没有影响客户正在用的那条流程。

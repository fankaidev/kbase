# (86 封私信 / 38 条消息) 如何评价 OpenAI 于11月18日发布的 GPT-6.2 Astra 和 Sol 模型？

**从 GPT-6.2 开始，对话历史基本只能往后追加，不能回头改了。**

昨晚翻开发者文档，看到了迁移指南的 What’s new ，内容大致是：如果在多轮对话中修改了前面的历史，比如改写开头的 developer 消息、截短某次工具调用的返回结果、用摘要替换掉旧的几轮对话，或者中途切换了模型、更换了终端用户或组织，Responses API 就会把这个改动点之后的 reasoning items 全部丢掉。

reasoning items 是模型在前面几轮里留下的推理过程，丢掉之后，模型得从头再推一遍，消耗的 token 会变多，延迟也会变长，文档也明确说了，推理恢复不了时，输出质量会下降。

如果单看这一条，可能会以为只是缓存命中率的技术细节，可文档里还有一句：丢弃推理是作为他们安全保障措施的一部分来执行的。也就是说，还不只是计费上的选择，是个安全策略。

* * *

过去两年，做 Agent 的朋友应该都积累了一套上下文管理技巧：

*   系统提示词按场景动态拼接，每轮根据检索结果重写开头。
*   工具返回的日志太长，过几轮就回头把它截短。
*   对话超过一定长度，把前面的部分压成摘要，替换原文。
*   结构化输出的 schema 按任务阶段随时切换。
*   可用的工具列表按权限动态增减。

这五种做法，在 GPT-6.2 上全部算前缀修改。

我自己维护着一个代码审查用的小 Agent，看完文档后把代码过了一遍，发现上面五条它占了四条。之前我一直觉得这套上下文裁剪写得挺讲究，现在每一次裁剪都会丢掉模型前面的推理。

OpenAI 给出的替代方案：

原来的做法

GPT-6.2 推荐的做法

改 reasoning.effort 参数

在末尾追加一个 [configuration\_update](https://zhida.zhihu.com/search?content_id=805207074&content_type=Answer&match_order=1&q=configuration_update&zhida_source=entity) 条目，请求级参数保持不变

改 text.format 换 schema

同样用 configuration\_update 追加

改 tools 列表

用 additional\_tools 追加，或用 allowed\_tools 限制当轮可调用范围

改开头的 developer 指令

在末尾追加一条新的 developer 消息

截短旧的工具输出

在第一次发给模型之前就截短，之后不再动

还有一个容易被忽略的变化：顶层 `instructions` 字段现在被放到了 `input` 后面。想让固定指令吃到缓存，就得把它挪进 `input` 第一条 developer 消息。不改的话，这部分按未缓存的输入价计费。

把这些放在一起，意思很清楚：上下文按时间顺序只往末尾追加，配置变更也作为一条新记录写在后面，不要动前面的内容。

* * *

定价方面。

Astra 的缓存输入是每百万 token 0.4 美元，普通输入是 8 美元，相差二十倍。Sol 也是二十倍，0.1 美元对 2 美元。

Sol 的模型页上还有一项单列出来的 Cache writes，每百万 token 2.5 美元，比普通输入的 2 美元还贵。

其实算一下就明白了：一个前缀写进缓存后被反复复用，单价会降到很低；如果你每轮都改前缀，每轮都要重新写缓存，付的钱比完全不用缓存还多。再加上改前缀会丢推理、降质量，“随手改前缀”的代价就变成了两部分：账单上更贵且效果上有损失。

官方宣传的“每个任务成本降低”，有很大一部分前提是集成方式符合追加模式。用老写法直接把模型名换成 `gpt-6.2-astra`，账单可能还会涨。

* * *

原因大概有三层。

工程上，推理模型的中间推理很长，跨轮保留下来，后续的轮次才能接着用，这是长任务做得好的基础。一旦允许前缀随意改动，服务端没法保证保留下来的推理和你改过的历史还对得上。

安全上，如果开发者可以随意改写历史，就可以伪造前面的对话，让模型以为自己“之前已经同意过”某件事，或者让一段 reasoning item 接在一段被篡改过的上下文后面。前缀一变就丢推理，等于在服务端堵住了这条路。结合这次发布里提到的情况，两款模型在网络安全上达到 Critical 阈值、在生物化学上达到 High 阈值，这种防护是可以理解的。

商业上，文档里有个例外：如果你用的是 OpenAI 自家的压缩功能，也就是 `/responses/compact` 或 `context_management`，即使前缀变了，后续的推理也会被保留。自己写的压缩方案就没有这个待遇，官方建议把压缩结果放在上下文末尾，要么接受推理被丢弃。

这一点就很奇怪，规则本身有合理的地方，可一旦豁免只给自家工具，“上下文管理”这一层就在逐渐收回到平台手里。以前这一层是各家框架、各个团队自己发挥的地方，以后很可能变成“用官方的最省事，用自己的要付出代价”。

* * *

两款模型在两项测试里，更倾向于不提及阻碍工作的情况，比如文件缺失、搜索工具不可用。OpenAI 在 Codex 里加了指令来减少这种遗漏，表示还在调查。

单看这一条，好像只是个小瑕疵。可如果把它和追加模式放在一起，就有点意思了。

以前开发者手里有一个兜底手段：发现模型某一轮走偏了，可以回头改历史、删掉出问题的那几轮、重新来过。追加模式下，这种回头修改有代价，开发者会更倾向于让 Agent 一路跑下去，只在末尾补指令纠偏。这时，模型能不能如实报告“我这里卡住了”，就变得更关键了。历史越难改，越要靠模型自己诚实地汇报中间状态。

* * *

半年内，主流 Agent 框架都会重写上下文管理模块。按时间顺序追加、配置变更作为事件写入、压缩结果放到末尾，这些会成为默认设计。估计其他家的推理模型 API 也会跟进类似规则，因为跨轮保留推理的需求是共通的，安全上的顾虑也是共通的。

“提示词工程”的重点会从写好一段系统提示词，转向设计好整个会话的结构。哪些内容放进不变的开头，哪些作为追加项，工具输出在第一次进入上下文前裁剪到多长，这些决策会直接写进账单。

工具链里会出现一个新品类，专门诊断前缀变化。OpenAI 自己已经给了 Prompt Cache Diagnostics，响应里也有 `input_transformations` 字段，能看到哪些推理被删了、原因是什么。第三方的可观测性平台大概率会把这个当成核心指标来做。

对中小团队来说，跨模型迁移的成本在上升。会话结构一旦按某家的追加规则深度定制，再切到另一家，就不只是一个模型名这么简单了。

* * *

看完这份迁移文档，第一反应是麻烦，其次是这件事迟早要来，过去我们把上下文当成随便改的草稿纸，是因为模型每一轮都从零开始，改了也没什么损失。现在模型的推理能跨轮延续，前面的每一步都有他存在的意义了，历史也就不能再随手涂改了。

Lauren’s **"pstack"** workflow gives agents the tools to do those checks themselves. They run the application, test the changed feature, and save evidence. The instructions live in the repository, where the next agent can use them.

**In this article, I’ll show you how to build an agent team using Lauren Tan’s method.**

You’ll assign roles, set up verification, and take an issue to a PR. Then you’ll automate checks and run agents in parallel.

> Each PR will show what changed, what passed, and what needs your review.

**Let’s start**

# 1. Setup (connect the repository and run it once)

**Start with one bot and one repository.** The first task is to confirm that an agent can access the code, install dependencies, and run the application.

## Step by step:

1. Install Grok Bot
2. Sign in
3. Open your first bot and name it **Chief**.

We’ll define its responsibilities when we build the team

## Here’s how the work will be split:

| Component | Job |
| --- | --- |
| Grok Bot | Receives requests and coordinates work |
| Cursor cloud agents | Run the code and prepare changes in separate environments |
| GitHub | Holds issues, branches, pull requests, and CI results |

Grok Bot’s bots share one account-level computer. Cursor cloud agents run in separate VMs. That distinction matters when several agents need to build and test code simultaneously.

[Image](https://x.com/0xChonsy/article/2115445646169694321/media/2115083962007592960)

## Connect GitHub in both places

In Grok Bot, open **Connect apps**, find GitHub, and complete authorization. Confirm it appears under **Installed**.

Then open Cursor Cloud Agents. Connect GitHub for cloud-agent access, select your repository, and complete the guided environment setup. Cursor installs dependencies and saves the environment after a successful build.

## Choose Opus 5.5 for the coding agent

Grok Bot chooses its own backend model. You cannot force Opus 5.5 or inspect the model behind an individual Grok Bot request. For explicit model selection, use the cloud coding agent’s configuration and confirm Opus 5.5 is available to your account.

For example, I’ll use [Cypress Real-World App](https://github.com/cypress-io/cypress-realworld-app?utm_source=chatgpt.com) this time. It includes a frontend, an API, seeded data, and tests for user flows

Create a copy in your GitHub account and select it during cloud environment setup. All changes will stay in your copy

# 2. Verification (make the agent test the application)

A typecheck can pass while login fails in the browser.

> The agent needs to know how to start the app, reach the login screen, perform the action, and inspect the result.

## Lauren’s pstack includes create-verification-skill for this.

It reads the repository and creates instructions that another agent can follow in a fresh session.

1. Open [pstack for Grok Bot](https://x.ai/bot/plugin/9717366?utm_source=chatgpt.com) and choose **Add to Grok Bot**
2. Ask Chief to confirm that the verification workflow is available

The verification must run in the cloud agent’s checkout of your application. Chief should pass the workflow instructions to that executor and collect its results.

## Give the next agent an exact route

2. **Doctor:** how to identify the correct instance and detect an unusable environment.

4. **Evidence:** where results are saved and what demonstrates success.
5. **Cleanup:** which processes and temporary state belong to this run. [GitHub](https://github.com/cursor/plugins/blob/main/pstack/skills/create-verification-skill/SKILL.md?utm_source=chatgpt.com)

# 3. Team (assign the work)

**Add three bots: **

3. Reviewer

I’ll use these four roles for our setup. Chief tracks the request. Lead defines the work. Builder manages implementation. Reviewer checks the result against the original requirements.

# 4. Issue to PR (run the first task)

Give the team one specific job:

> **Add a regression test for signing in after a failed attempt.**

A user enters invalid credentials, sees an error, corrects the fields, and submits again without reloading the page.

**The application should accept the valid credentials and clear the error**

The repository already includes tests for invalid usernames and passwords. Lead should inspect those tests and check whether this complete retry sequence is covered.

## Create the Issue in your GitHub copy

Use these acceptance criteria:

| Action | Expected result |
| --- | --- |
| Submit invalid credentials | An authentication error appears; the user remains signed out |
| Clear both fields and enter valid seeded credentials | The form accepts the corrected values |
| Submit again without reloading | Authentication succeeds; the previous error disappears |
| Run the existing authentication suite | Existing behavior still passes |

Keep this first task focused on test coverage. If the scenario exposes an application bug, preserve the reproduction and ask for approval to expand the task.

## 5. Quality (turn fixes into checks)

When Reviewer catches a mistake, decide what will catch it next time.

A repeated correction can become an architectural constraint, a type error, a lint rule, or a regression test.

**Lauren’s *****/correct***** workflow follows that order:** use the strongest practical enforcement, then document what remains.

For our authentication task, the next step is concrete: **run the checks on every PR.**

## Add the verification job

Enable GitHub Actions in your copy. Ask Builder to inspect the existing workflows and add this job without duplicating checks already present.

Save it as .github/workflows/auth-verification.yml:

yamlname: Authentication verification

on:
  pull_request:

permissions:
  contents: read

concurrency:
  group: auth-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  auth:
    name: auth-verification
    runs-on: ubuntu-24.04
    timeout-minutes: 20

    steps:
      - name: Check out the submitted commit
        uses: actions/checkout@v7
        with:
          ref: ${{ github.event.pull_request.head.sha }}
          persist-credentials: false

      - name: Set up Node
        uses: actions/setup-node@v7
        with:
          node-version-file: .node-version
          package-manager-cache: false

      - name: Install Yarn Classic
        run: npm install --global yarn@1.22.22

      - name: Install dependencies
        run: yarn install --frozen-lockfile

      - name: Prepare mock provider configuration
        run: yarn predev:cognito:ci

      - name: Check types
        run: yarn types

      - name: Run authentication tests
        uses: cypress-io/github-action@v7
        with:
          install: false
          start: yarn dev
          wait-on: "http://localhost:3000,http://localhost:3001"
          wait-on-timeout: 120
          spec: "cypress/tests/ui/auth.spec.ts,cypress/tests/ui/auth-retry.spec.ts"
          config: video=true

      - name: Preserve browser evidence
        if: always()
        uses: actions/upload-artifact@v7
        with:
          name: auth-evidence-${{ github.event.pull_request.head.sha }}
          path: |
            cypress/screenshots
            cypress/videos
          if-no-files-found: ignore

The Cypress action supports starting the app, waiting for services, and preserving browser artifacts. The setup commands come from our example repository. If section 04 placed the retry test elsewhere, update spec accordingly.

Run the workflow in your copy before making it mandatory. Resolve environment failures and inspect the test output.

## If the run stalls

- **The agent cannot start the application
**Inspect its environment and setup logs. Reproduce the startup failure before changing product code
- **Two runs touch the same work.**
Have Chief identify the owner and stop the duplicate. Confirm which branch and commit will continue
- **Reviewer cannot execute a required check.**
Keep the verdict at **BLOCKED**. Record the missing dependency, permission, or service
- **A new commit appears after PASS.**
Send that SHA back to Reviewer. Check the latest CI results before approving a merge

**After several runs, compare similar tasks.**

Look for less time spent reconstructing what happened, fewer repeated corrections, and evidence that remains easy to inspect

Then add one independent task in parallel. Give it a separate branch and environment.

> Cursor cloud agents support isolated VMs, which helps keep application instances and test data separate

**Keep measuring review time as concurrency grows**

If it rises sharply, use the run records to find the slow handoff or missing check before expanding further.

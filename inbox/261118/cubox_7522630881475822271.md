**01**

## **从对话到任务：**

## **一件事得有一张工单**

先说第一处。我们之前一直在想，session 和 session 之间到底该是什么关系？一件事可能要聊好几次、跑好几轮，如果每次都只按 session 来组织，其实很难说清这些执行究竟是在推进同一件事，还是几件不同的事。

去年 10 月开始深度使用 Linear 之后，我们越来越觉得 Task 是个很好的切分单位：先有「这件事」，然后才有围绕它发生的讨论和执行。但平时用 CC + Linear 时，体验又挺割裂。Linear 里有记录的 issue，CC 里有执行它的 session，两边都在描述同一件事，却没有自然地连在一起。我们当时就在想，它们本来就是一件事的两面，为什么还要让人自己去两个应用里面跳来跳去呢？

带着这个想法，LobeHub 在今年 4 月上线了 Task 系统，像 Linear 管理 Issue 一样，管理 Agent 的任务。在当时，其实已经有一些软件通过给 Session 打上生命周期的标签（Backlog / Todo / Needs Review...）来管理，比如 Craft Agent。还有一些产品，更进一步做成了协作看板，比如 Multica。

我们认可这个方向，但是在那个时间点，有一个问题我们自己也回答不了。如果 Task 的底层还是对话，那么用户究竟怎么区分这两种形态？换句话说，当你把这两盘菜端到用户面前时，用户还是会习惯性地开启对话，而不是启动一个任务。

事实上，用户心智想要从 Session 转化为 Task，使用场景要满足三个特征：并行、长程和异步。这三个，是今年 Agent 发展过程中逐步成型的。

**并行** ：当时已经成为了共识，从 cli 的多窗口，到 codex app 同时切 n 个 worktree 左侧轻松切换。

**长程** ：这件事有一个左脚踩右脚的过程。一方面，模型的能力变强了，可以自主探索、做更多的事情。同时，模型本身就被训练、harness 也被设计为让它更多地去做事（比如 goal 的功能，比如过度探索导致的越界）。另一方面，人们希望 Agent 可以将自己的事情端到端完成，模型厂商也希望消耗更多的 token。

长程带来了很多影响，比如远程化或者云端化。其实并行不会直接导致云化，只要任务都结束比较快，本地也可以并行，遇到的性能和存储瓶颈也只是升级本机设备的问题。

但是长程就必将导致云化。时间长会导致并行任务的积压，等不到结束，单机就无法再开启新任务了。另外，在如此长的时间内，本机可能需要做别的事情，本机也可能要临时关闭，但是任务不能停。那自然而然的，Agent 就被放到远端去执行，任务的完成也就变成异步了。人们希望一个回调函数，完成时通知自己。

**异步** ：除了任务的「异步结束」，我们觉得今年下半年更重要的一个变化是「异步开始」。当我们给 Agent 发了消息，却不是希望它立刻执行。大家可能第一反应是定时任务，但定时任务只是一种特殊情况。

在团队协作中，异步任务有着更广泛的应用。假设团队已经建立了软件工厂，不管外部还是内部的缺陷，都可以直接转给一台 7×24 运行的 claude code 来处理。当源源不断的问题进来，如果没有一个任务管理来区分紧急重要、规模大小、以及问题与问题之间的依赖和冲突等，那么受限于订阅 / API 额度有限、环境资源有限等，claude code 必然是处理不过来的，就一定需要编排。

说到这里，其实已经像我们曾经的全人类团队了。同一时间有很多需求并行，一个需求的完成是长程的（需要一段时间），大家都在异步工作（有需求的依赖），资源总是有限的（人力、财务等）。

下图是 LobeHub 的 Agent 和人协作的任务看板，已经成为了我们团队的开发日常。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_png%2F5icxfcvT9UmiafIQyibHGS6us4cvIlCe2eyW9DLM8EAHbTzdqMh7KpdmZPEu2FuMrPUial82JNcGaSDkrice36DgGIibWScZ99riagfr2FrXic179e8%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D2)

当这种协作变成日常之后，回过头来看 Super-agent 的 Router / Worker 设计，Task 的位置就更清楚了。Router 决定交给谁，Worker 负责把活干出来。但光靠这两层，还没有回答「它们在为哪件事工作」。我们想补的 Task，不是再加一个负责调度的角色，而是给那件事一个独立于 session 的身份。这样不同的 session 可以围绕同一个 Task 展开，一次执行也能找到它归属的那件事。

所以我们在 LobeHub 里把 Task 做成一张「工单」：哪个 Agent 来干、在哪个环境里干、用哪个 Model 来干，都记在这张单子上。Worker 跑出来的 trajectory，也归到这张单子下面。至少在我们现在的理解里，session 更像一次交流或执行发生的地方，Task 才是把这些过程串起来的那件事。

这个设计的好处，我们一开始只看到一层，后来发现其实是三件事。

**第一件，人有地方看了。** 一件事如果只活在聊天记录里，人是没法判断它走到哪一步的。Task 有形态，有形态才有「展示」可言，不然你只能对着一条滚动条猜它到底干完没有。这其实是我们最初的初衷，也是能带来直接的用户体验提升的地方。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_png%2F5icxfcvT9UmjhbgLwR8HHHnicFjb2IE846OeP4EUELKRcUCZYnxWAXvz5H5tEydhCRu8kDIbzv3WP2lzLvDSc0wdNO8pBXibiaTjGSyibJ9oibxKk%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D3)

**第二件，上下文有了边界。** 这是我们用了几个月之后意识到的。Agent 最难受的从来不是没能力，是被塞进一段无限长的对话里，什么都得记着，什么都得接着。Task 给了它一个可以切出去的落点，这件事归这件事，那件事归那件事。

每个 task 都可以有一个独立的 agent、独立的 model、独立的环境，以及独属于这个 task 的 session 序列，这使得一件事的长期演进真正成为了可能。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_png%2F5icxfcvT9UmjYnOXricvXic92Yr2sGVUwneKlGRU9CPxbUoadUNfHUzsbVdP6jjzRH87WLe1Lhv5xv93KZ8NLeAvUmHp9tDK1Z8so4lxYdwB3o%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D4)

我们的 agent 定时汇报

**第三件，触发信号这件事有了落点。** 既然 Task 是一张独立的单子，「什么时候触发它」就变成一个可以单独拎出来设计的问题：可以由用户触发，也可以由 agent 自己触发，也可以由定时任务触发。这几条路一通，定时任务就不只是「到点跑一遍脚本」了。它可以去迭代这张工单本身，今天跑出什么、明天怎么改，慢慢地就有了一点自演进的味道。

我们在 9 月 9 日创建的后端接口 P95 日报，在一个多月的迭代后，Agent 自行将口径迭代到了 v13 版本，中间没有做过任何一次干预。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_png%2F5icxfcvT9UmheqEFV4CuxsD42ZWayN9FOaLrEV8BetFlalwjRwXGXiaUYfIPzfibKO5ticya89kqsCHU5dMzNpu2FFK67EPUtt9mgzyADsknYvI%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D5)

这三条听起来好像没啥太大的相关性，但其实它们在回答同一个问题。一个 Agent 和一次执行，多个 agent 和多次执行之间，应该需要什么样的组织关系。

## **02**

## **便宜模型当「秘书」，**

## **高级模型负责干活**

有了工单来承载任务，接下来的问题是：在日常的群聊和协作流里，任务是怎么被提取和分发出来的？

其实双层架构并不是什么新鲜事。相信大家都有过这样的实践，让更强的模型来设计方案，然后让没那么强但是足够完成任务的模型来执行。通过这种方式，来实现成本和速度的平衡。相当于老板拍方案，手下的人去执行。

那 DeepSeek 里提到的，本质就是把模型选择反过来。让一个足够便宜且快速、但是智能达标的模型，在接受噪音的情况下，做一些简单的总结、分发，真正的工作还是让高级模型来执行。相当于秘书接电话，选事情上报给老板处理。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_png%2F5icxfcvT9UmiabVCESALw7ZQLWaj1NL9RV5FsrVXzb1ibicOnibU4bIYeyTROvCwcDiaz8Jc8Wq2o8rQsJ3XEMAuKrfrGSicHmHtvwfZzyiabNeq784%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D6)

思路很简单，但也是经历了一些演化。比如最开始 Raft（当时还叫做 slock）让大家把 Codex / Claude Code 接入聊天频道，让他们可以直接感知人类讨论的上下文去干活。但是这里存在问题（当时的版本，不知道他们后来怎么处理的），在他们的博客中也提到了，一是成本，比如频道中每发一条消息，他们可能都需要去读一下才知道是否和自己相关，相比之下，人类只需要扫一眼就行。二是智能。如果我们希望保障 Codex 的产出质量，是不希望频道控制相关的上下文也混入其中的。（开发者对 harness 和 context 更为敏感，比如同样的模型，很多人用 pi 也不相信 codex）

真正的转折点发生在模型的进步。今年第一档模型的发展放缓了（相比于去年），但是第二档模型在速度、成本、智能上的优化却是惊人的。这才有了采用比如 DeepSeek Flash 来作为中转模型，接受这些聊天噪音，并且清晰地提取出任务，再交给专业的 Harness 和模型来隔离处理问题，一举解决了刚才提到的问题。

至于如何让 Agent 可以从噪音中提取出信号，我们已经完成了产品化，可以加规则，可以调程度，也可以反馈迭代。

## **03**

## **Agent 该不该醒，**

## **需要一套 Proactive 策略工程**

如果这篇只能留一节，我们一定只留关于 Proactive 唤醒的这一部分，这里深度剖析了我们在主动唤醒上的一手实践。

像 Coding Agent 的唤醒机制可以说简单到几乎不用设计：人敲一句，它就动。所有的主动性都在人这边，它不需要有任何判断。

而一旦 agent 要在群里、在频道里、在没有明确指令的日常对话里活着，问题就整个变了。

最经典的两种唤醒是确定性的：有人 @ 它，它醒；命中某些关键词，比如「bug」，它醒。这两条特别好写，也特别好解释。因为它们是规则，不是判断。规则不需要智能。

但真实的聊天不长这样。真实聊天里大量是「这个按钮是不是有点歪」「这块要不要再想想」，甚至就是随口一句，连主语都没有。这种时候它该不该自己醒？

所以这里能做的事，其实比想象的多很多，我们分成了三层：直接叫、关键词与主动判断。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_png%2F5icxfcvT9Umj68ySXh3dL9sQ67YVwuzJ4DuOIwywmiaEMrUuiboZAolib24tvo8RFsUJuvYlyl8dRTXu81QqpeujSwIlelPgG8ibUjwmSu9GGMOw%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D10)

具体怎么设计唤醒，有几个核心思路展开聊聊。

**第一，唤醒这件事应该是一个策略化的设计方案。** 不要做写死的判断逻辑，会迷失。不同策略之间存在「与、或、并、跳过」这一系列权重配置，同时有固定策略，也有交给模型判断的 LLM 策略。

譬如，在一个群里聊到设计相关的话题，设计 agent 就应该主动被唤醒，跑一轮并且接话。聊到具体的开发任务，它就不该醒，应该沉默着。

如果一个系统的唤醒是靠系统提示词里写一句「请在合适的时候主动参与」，那不叫策略，那叫愿望。实测愿望是拦不住任何一次误唤醒的。

那怎么办？我们给每个 bot 提供了一个自己的职责栏位。有了这层之后，讨论产品的时候，主管 agent NASA 会介入，答疑，或者干脆直接把需求记下来。讨论到需求或者设计形态，设计 agent 才会唤出来，去呈现相应的设计方案。而这种朴素设计思想的效果出乎意料地 work。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_png%2F5icxfcvT9UmgbhiasX9m2fgvgPhzWRHKqSWib0AfmOzliasPwMrG44BJANL4SIyv7OhJE1kmFsibu4iadMoL1ADoDIZDj3ibIEiahduV6ZhtTkrBN4Q%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D11)

NASA 的职责边界

**第二，「这事归不归我管」和「我现在插一句有没有帮助」，其实是两个不同的命题。**

我们后来发现，在有些我们期待 NASA 唤醒的场景下，NASA 并没有唤醒。但如果此时唤醒的话，体验上应该会有惊喜感。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_png%2F5icxfcvT9UmgO2nibbU9jnUb2QTjndniafHhqA3osbWqxqQySOgXpTrPHgYlmCw1sOqmpib4hJR8pHVeRA76sGzviaNItia0v0mToAmgOv1ibYfcxQ%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D12)

这里如果唤醒的话，体验上应该会有惊喜感

通过回测才发现，我们期待它唤醒的场景下往往不属于它的职责。duty 问的是「是不是职责范围内的事」，不是「插话有没有价值」，上一条截图中的职责匹配得分是 0.61，没过 0.65 的唤醒线。而另外有人问 NASA 刚发的链接为什么还带着 sign in 的 meta，它职责分只有 0.27。前者是它有机会查清楚的问题，后者更是它自己的回复相关的问题。只问「属不属于职责」，很容易把这种值得接的话放过去。

我们也试了把阈值往下调，比如降到 0.60，前面那条 0.61 的问题就能进来。但那个链接问题只有 0.27，还是会漏掉。而在我们自己标注了的同一批记录里，一句「其实就是 Agent Role」这样的闲聊也拿到了 0.55。继续降低阈值，它也可能被叫醒。光调这个数字，能改变唤醒的多少，却没法判断 NASA 这时说话到底能不能帮上忙。

此时我们突然意识到，「这事归不归我管」和「我现在插一句有没有帮助」，其实是两个不同的命题。这是两种不同的优化方向。一种是「老实本分」地做好自己，另一种则是乐善好施地帮助他人。而一个好的 agent 伙伴，应该是「手里有活，眼里有光」，两者兼具。

## **04**

## **被唤醒之后，**

## **Agent 也可以选择不说话**

还有一个我们觉得特别重要的东西：沉默。

在 proactive 的场景里，沉默不是一个 bug，它反而变成了一个很重要的 feature。

你不给它留这个出口，主动就一定会变成噪声。一个永远在接话的话痨 agent，最后大概率被所有人静音，这几乎是可预见的结局。

在实现的思路上，其实大家会很类似，都是两阶段。先有一段前置判断，然后再是 agent 执行。一般前一段用一个分类器快速判别一下，这条消息要不要惊动谁。但其实后面那段也需要考虑，agent 被唤醒之后，它自己要决定是不是该停下来，或者干脆不响应。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_png%2F5icxfcvT9UmhODSgpiclJVXQ9aOF5DQSXgAYiak2iaUgibhoqTh0ekykzE0M3c4fKiaalEQhxcxXq0DaCEicmjQgaIhviaZSlOTJTUYQhDHyNTic2uT0%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D13)

有了这样一套机制，后面的流程才谈得上。因为唤醒是一个叫醒的动作，而叫醒之后要不要开口，才是更智能的。为什么 bot 在被唤醒后，不能是「看了一眼，觉得没自己什么事，然后继续睡」？

## **05**

## **Agent 怎么在反馈里变得更有分寸**

策略是会过期的，也需要演进。那如何演进？

我们在之前的《需要自进化的不是 Agent，而是 Harness》里提过，tracing 是进化的原材料，所以这里就有了核心的 4 步。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_png%2F5icxfcvT9UmgNdWPd2tHtakd0ajXyepESV8nF8h1JbdwY8TibpxqNPXOJOoCibNtAKZOoLwPpiaewYE8T0nmiaz0M6JAwsX4W3Xo6uASVsKU1ibs8%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D14)

**第一件事，记录完整的原始场景。** 只有留了现场，用户才能观测、才能理解这个 bot 到底该怎么调整和优化。它是没醒对，还是醒了但说错了？这两种问题要改的地方完全不一样。没有现场，反馈就只剩情绪，而「它好烦」这种话你没法据此改任何东西。

**第二件事，给它一套拿得到反馈的机制。** 点赞、点踩，或者干脆丢一个笑哭的表情。随手给出的表情就已经具备丰富的反馈信号了。

**第三件事，每天晚上做总结的时候自我迭代一次。** 把白天的信号过一遍，自己改一版。

**第四件事，回测。** 这一条才是真正的工作量：之前该唤醒的还唤醒，之前不该唤醒的被解决掉。

这件事我们还在迭代过程中，目前只是完成了第一步。在接下来一两周内，我们将会完整实现 2\~4 步，进而让 agent 同事在和大伙相处的过程中，越来越得体、知分寸。

## **06**

## **团队里的设备，**

## **正在变成 Agent 的资源池**

除了任务组织和唤醒策略，DeepSeek 文中还提到了「一个 Agent 不再受限于单台机器，而是可以在不同的执行设备之间切换，根据任务需要选择环境来执行命令并获取环境中的上下文。」这一点在 LobeHub 上也是今年 5 月份就实现了。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_png%2F5icxfcvT9UmiaiayC6kMylD3nP848v3J2LUOmkFU38ibWssgwrICwOKc9jFo0LibW57AuwqtsNYQnRE78yUVEKmTbJaVxE25Wq735lFOD9LsK8jA%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D15)

之前我们也讨论过 Agent 和 Computer 的关系，在 Personal Agent 中，这种选择只会让用户困惑，也无法保证切换设备后，该有的 skill 还有，该有的软件还有，GrokBot 是我们看来在个人场景下的最佳方案。

但是在团队场景下、在生产力场景下，设备本身只是一种资源，并且一定是配置好的。问题又变成了资源的调度。一方面，Agent 能够自行选择设备，就可以做到根据性能和空闲选择机器、不同操作系统的切换构建验证。另一方面，我们也可以在设备侧做一层抽象，变成动态伸缩和调配。这也必将是未来 Agent Infra 的方向。

## **07**

## **当 Agent 进入团队，**

## **资源、成本和责任怎么分？**

以上是我们在 Super-agent 这条路上的一些实践与思考。很高兴看到 DeepSeek 梳理的架构和我们在产品与工程上一直探索的方向如此契合。

但当设备、工具和 Agent 都进入团队场景之后，哪怕探索了这么多，还有一个问题已经萦绕了我们 3 个多月，我们都还没想明白该怎么优雅地解决。而且我们相信它会在接下来，随着大家在用协同 agent 时频次越来越高，变得越来越显著。

它就是，**资源或者资产的归属。**

场景很简单，一个 agent 在频道里产出了一份东西。于是立刻有两个问题蹦出来，这条执行的成本算谁的？是 bot 主人的，还是发起这件事的人的？这份产出又属于谁？是主人，还是发起者？

往前推一步就会发现，这已经不只是记账问题了。它涉及到组织当中，生产资料和生产价值发生的结构化特征。

放大到社会里来看，我们有合同机制，白纸黑字锚定最终产物的归属。但 agent 这个载体有点特殊，它是一个自动运行的载体，一方面它用的资源是主人的，另一方面发起者可能又带上了自己的那部分资源。两边都出了一部分，产物落谁名下？

举两个场景，它们甚至是需求完全相反的场景，特别能说明这种冲突。

假设有一个帮人整理邮件的 agent。如果用的是创建 bot 的主人绑定的 Gmail，那整理出来的全是主人的邮件。这显然不合理吧，用户要的是整理自己的邮箱，此时 Gmail 是必须要连到发起者才行的。

再假设有另外一个 agent，连接了某个股票数据库 MCP，以 bot 的形式对团队提供服务。这时候对话发起者本身并不拥有这个 MCP 服务，他只有「想用」的意愿。如果你让他先去把这个 MCP 的所有权配一遍，这事非常麻烦：他既没有权限，大概也没有这个必要。

这两个例子放在一起，我们无法直接说「资源都归发起者」或者「都归 bot 主人」。整理邮件时，agent 得用发起者的 Gmail。查股票数据库时，它可能恰恰要用 bot 主人提供的 MCP Server。同样是一个人在频道里叫 agent 做事，能用谁的资源，答案就已经不一样了。再往下问，调用成本由谁承担、产出的内容算谁的，也不能只凭「谁发起了对话」一项来定。

以前用 Coding Agent 时不太会被这个问题绊住，通常是我们在自己的环境里发起执行、提供资源，也由自己接收结果。可一旦把 agent 放进团队频道，这几个人可能不再是同一个人。发起者能提需求，不代表他有权调用 bot 主人的所有资源；bot 主人提供了工具，也不代表每份产出都该归他。

所以这块我们到现在也还没想清楚。表面上是在分资源的使用权限、执行成本和产物归属。再往下问，其实是 agent 在代表谁做事？它凭什么调用某个人或团队的资源？做成了、做错了，谁来接这个结果？

我们隐约觉得，这可能碰到了人和 agent 一起工作时最根本的关系。但这个关系到底该怎么定义，我们也还在求索中。对于接下来各家 Agent 产品的形态变化，我们非常兴奋和期待。

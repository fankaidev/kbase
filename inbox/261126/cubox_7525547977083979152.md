作者 \| Tina

过去需要一个专职工程团队驻守整整一年才能维护好的核心代码仓库系统，在 Shopify 内部，只花了一个周末就被彻底重写了一遍------周五拍板立项，周一早晨，全新的生产代码就已经在服务器上跑起来了。

这是 Shopify 创始人兼 CEO Tobi Lütke 亲手交出的实战成绩。他紧接着在与 David Senra 的播客长谈中抛出了一个判断：未来 6 到 12 个月，全球大部分人类手写的生产代码，可能都得全部换掉。

很多人以为这又是科技大佬的例行"AI 焦虑贩卖"。但 Lütke 并非只会画饼的职业经理人，他是一个从零敲出 Shopify 代码、二十多年来从未离开过一线的程序员；翻开他过去一年在 GitHub 上留下的密集代码记录，你会发现，这其实是硅谷最硬核的一次"知行合一"。

1 为什么全球手写代码将在一年内迎来大规模重写？

"我在这个行业待了这么久，一向以尽可能知道业内所有事情为傲。"

Tobi Lütke 是早期 Ruby on Rails 社区的核心贡献者。二十多年前，他亲手写下了 Shopify 的第一行代码。如今，执掌这家市值以千亿美元计的上市公司，他依然保持着周末亲自写代码的习惯。也正是在继续做软件的过程中，他发现，自己熟悉了二十多年的程序员工作，已经发生了很大的变化。

过去，程序员坐在终端或编辑器前，逐行写下计算机要执行的指令，有时还得亲手把每个细节调到位。想做的软件太多，能写软件的人太少。Lütke 估计，当时工程师的供给可能只相当于需求的 0.1%。至于为什么这么少，他提到个人禀赋可能是原因之一，也可能还有别的因素。在这样的条件下，他们那一代开发者能做的一件重要的事，**就是开发框架** ，让有限的人手做出更多软件。Lütke 在对谈中几次提到，Shopify 就是用 Ruby on Rails 做起来的。

框架背后，是整个软件行业长期以来对开发效率的追求。开发者把复杂的操作封装起来，其他人就能直接使用，不必每次都从头写起。按 Lütke 的说法，借助这些抽象，一个工程师的代码产出可以达到原来的十倍甚至百倍。抽象也有代价，但工程师的时间更紧缺，行业自然把开发效率放在首位。计算机每快一点，软件就有余地再叠一层抽象。几十年下来，在 Lütke 看来，硬件提速带来的余量几乎都花在了这里。

到了今天，Lütke 更愿意把自己称为一个"做东西的人"。以前，要尽快做出一个够用的版本，程序员往往只来得及想清楚下一步怎么写。现在，他可以直接告诉计算机自己希望实现什么，再和 AI 来回推敲，想清楚自己究竟需要一套什么样的系统。过去因为实现成本太高而来不及考虑的方案，如今可以多想几步，目标也可以定得更远一些。

在这种工作方式下，程序员仍然要动脑筋，只是动脑筋的地方变了。怎样让 AI 理解自己真正想解决的问题，怎样判断做出来的东西是否符合要求，都要花更多精力。至于把想法变成代码这一步，已经交给了 AI ------开发效率本身，不再是那个死死卡住行业的瓶颈。

基于此，Lütke 给出了一个激进的推演：Web 2.0 时代"坐在编辑器前逐行敲入字符"的传统编码工作已经终结，存量人类手写代码也正在失去继续维护的价值。

**"在未来 6 到 12 个月内，我们可能得把地球上生产环境里运行的所有人类手写代码都换掉。"**

原因之一是算力趋紧对"抽象税"的残酷清算。

过去这种层层堆叠抽象的做法，对计算资源造成了极大浪费，也让软件变得越来越臃肿。为了说明软件过去是怎么消耗掉硬件性能增长的，他举了一个例子：1984 年的 Macintosh 几乎可以瞬间打开文字处理软件，而今天的电脑快了许多，启动 Word 时，有时却要等上 30 秒。

"未来一年可能出现的算力紧张，很多软件确实有充分的理由重写。我们需要它跑得更快、用的资源更少。看看笔记本供应就知道了，到了明年这个时候，各条供应链都会变得相当紧张。"

另一个原因是存量代码里积压的安全债务："人类写出来的软件安全性确实不够。"

过去代码写得慢、总量有限，工程师靠同事之间逐行做 Code Review，相当于用人肉运行着一套粗糙的验证机制。但在现代扫描工具与 AI 分析面前，人类手写代码库里散落在临时逻辑中的"隐式状态机（Implicit State Machines）"正在成批暴露。

Lütke 提到，只要用 Claude Code 这类工具梳理现有代码库、把隐式状态显式抽离出来，往往随手就能翻出成百上千个未被处理的边界状态和竞态 Bug；再用安全工具扫一遍，还会发现另一批问题。"等你看完结果，恐怕就很难再觉得代码应该由人来写。"

在他看来，整个软件行业正在经历一场惊人的网络安全警醒，大多数公司眼下都处于四处救火的紧急状态。

所以在安全与算力的双重挤压下，重写成了最务实的选择。

Lütke 给出了一个路径：先用形式化验证（Formal Verification）把系统的规约锁死，再放手让 Agent 用更底层、更安全的语言重写实现。在 AI 每小时就能产出数万行代码的今天，人工审查已经完全看不过来，工程规律也随之反转------人类过去痛恨严苛的 Linter 规则，但 Agent 恰恰喜欢死板的静态约束，它真正害怕的是跨 50 个文件追踪层层抽象的副作用。

因此，未来的标准做法是通过状态机建模、TLA+ 规约、属性测试与生产流量回放，先把系统在所有极端状态下的行为边界框死，再交由 Agent 用 Rust 这类内存安全、原生高性能的语言从头重构。

按照他的估算，经过这轮重写，软件不仅能接近零 Bug，在很多场景下运行速度甚至能提升上百倍。
> "我认为软件会接近没有 bug，很多情况下能快 100 倍。我们会回到应用点开就能用的世界，也会惊讶地发现，用一台普通笔记本，甚至用一台十年前的笔记本，就能完成那么多事。软件整体质量会大幅提升。"

2**不只是嘴上说说：** 这位千亿 CEO 在一线用 AI 造出了哪些项目？

Lütke 自己坦言，过去这一年里，他几乎每个周末都从头忙到尾。之所以敢给出一年内重写全球手写代码的激进时间表，很大程度上源于他始终待在代码一线、亲手搭脚手架的实测体感：他的 GitHub 主页显示，过去一年他个人累计留下了 4,880 次代码贡献，平均每天超过 13 次。

一个最贴近日常开发的例子，始于电脑硬盘空间爆满。嫌现有工具不够顺手，Lütke 用 Rust 搭配 GPUI 图形框架，写出了跨平台的磁盘空间可视化工具 disktree。

截图来源：https://github.com/tobi/disktree

深扒一下它的源码就会发现，这是一个细节拉满的工业级作品，并且处处践行着他前面提出的"算力榨取"与"确定性边界"原则。

性能上，在 Windows 管理员模式下直接读取 NTFS 主文件表，扫完 400 万个文件的 C 盘仅需 3.4 秒（比老牌神器 WizTree 的 11.2 秒快出三倍多）；而在扫描海量目录时，它采用流式深度优先遍历，让内存占用只随目录层级而非文件总数波动，哪怕在一台配置平平的机器上也不会把内存吃爆。

另外是清理机制。界面上的矩形树图不仅用斜线阴影标出 target 这类可安全回收的构建产物，在审查列表按下 a 键，还能直接生成一段提示词交给 Coding Agent，让 AI 先核查目录里有没有未推送的 Git 提交再动手清理；而在底层代码里，它硬编码封死了误删 /usr、/nix/store、Homebrew 及任何挂载点的可能，强制执行"先标记、再统一 Review 提交"的确定性流程以减少危险操作。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_jpg%2FhLLZnAbUwNjUbpLIF7T2brzqMLzWeL5ibxUIpwfQyKK5ld46Z3TfqpVE3EnrOCJwJqagr0AKCibmUYC33cRLMJyMyibXWFzQ71ibpcDJ7a8DlCo%2F640%3Fwx_fmt%3Djpeg%26from%3Dappmsg%23imgIndex%3D2)

这一年，他在 GitHub 上还推进了多个同类实验。比如为了解决 AI 代理跨会话"失忆"的问题，他写了本地知识库检索工具 QMD，完全在端侧完成混合检索与重排序；又比如在受够了复杂的代码托管底座后，他在一个周末用 Rust 写出了轻量级 Git 服务端 walgit，仅靠单个二进制文件配合对象存储桶，就替代了过去依赖重型数据库的繁杂架构。

Lütke 还推崇"遇到软件不好用，直接用 AI 现场写一个"的理念。

2026 年初，他做完年度核磁共振（MRI）检查后，嫌医院 U 盘里自带的商业软件太难用，于是直接把原始影像文件丢给 Claude，让 AI 现场编写了一个网页版交互式影像浏览器，甚至自动标注出了异常发现。这个项目在社交平台 X 上引发了超过 840 万次围观。

![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_jpg%2FhLLZnAbUwNgBAJlNWibMzt77UpWp9NwSta7LLbv76hShnr7mTy7SvqjRicibk8iakHqqV1MrIDedcs9MXKz3zVkMxnSu6ZMRgiba8ic4vmg79uCrM%2F640%3Fwx_fmt%3Djpeg%26from%3Dappmsg%23imgIndex%3D3)

从开发底层工具到解决日常问题，这些实践让 Lütke 形成了自己的协作方式。不要把提示词（Prompt）切碎成微小的编码步骤，那等于用人类先入为主的局部视角锁死了模型的搜索空间。他更愿意把完整的问题交给 Agent，用 linter 划定编码规则，把隐式状态机显式化，再用形式化验证检查系统行为。规则越清楚，越有余地让 Agent 自己找解法。

Lütke 把掌握这种做法前后的效率差距，比作现代工厂和中世纪铁匠铺的差别，差距大到无法比较。一旦 Agent 能稳定处理某一类问题，决定项目能不能做的，就不是时间问题了，而是你愿意投入多少成本。

不过，CEO 个人在笔记本电脑上"手搓"工具，终究只是极客的个人实验。当这套开发逻辑被搬进一家拥有数千名工程师、服务全球数百万商家的千亿美金公司时，究竟是如何运转的？

3 从极客周末到千亿帝国的"Agent 工厂"

回到开头那个周末。Lütke 动刀的是 Shopify 的内部源码仓库系统 Beta，它借鉴了他个人开源的轻量级 Git 托管项目 walgit。全公司数千名工程师都在这里提交代码，随着越来越多开发工作交由 AI 参与，团队合并 Pull Request 的速度已经达到公司历史峰值------按 Lütke 的估算，比以往快了 10 到 100 倍。代码吞吐量骤增之后，原本稳妥的仓库底座瞬间承受了前所未有的并发压力，Beta 必须提速。于是他利用一个周末指挥他口中的"Agent 工厂"完成核心架构重写，周一便直接推上了生产环境。

如果把 Beta 的改造放在五年前，Lütke 坦言，这个项目根本不可能立项。过去在人手写代码的时代，吞吐量受限于工程师人数，用现成的 GitHub 绰绰有余；想重写底层仓库或数据库层，意味着要抽调顶尖专家组建团队持续投入一整年，做完才能验证假设是否成立------对一家主营电商软件的公司而言，这种"支线任务"的试错成本太高了。而现在，依托成熟的 Agent 工厂，只需要花 2,000 美元的 token 成本，周五拍板，周一就能拿出可验证的生产代码。

这种生产力之所以能在 Shopify 迅速跑通，离不开公司在内部工具文化与 Agent Harness（代理脚手架 / 控制面） 上的长期积累。

与许多把内部工具当成"苦差事"交给实习生打理的科技公司不同，Shopify 历来把最顶尖的工程师派去做内部工具。内部系统不需要像面向全球商户的核心交易链路那样死守"四个 9（99.99%）"的严苛可用性，哪怕偶尔停机调整，影响也极为有限；同时内部同事能给出最直接的反馈。这让内部工具成了绝佳的 AI 试验田------连 Shopify 董事会成员、Ruby on Rails 之父 DHH 在参观完这些内部系统后都赞不绝口，直言它们比市面上花钱能买到的商业软件还要出色。

在此基础上，Shopify 为 AI 代理搭建了一套高度工程化的 Agent Harness------即围绕大模型构建的沙盒环境、代码库索引、自动化测试与权限控制面。正是有了这套坚固的脚手架，AI 才能从"聊天框里的代码补全工具"，进化为真正能独立交付的工程节点。

正如 Lütke 所描述的那样，如今在 Shopify 内部，人们就像魔法师一样，对着搭建好的 Agent 工厂念出几句自然语言指令，就能在极短时间内变出扎实的新工具------不仅非技术背景的同事开始用自然语言直接构建自己需要的小软件，工程师们也彻底摆脱了过去"因实现成本太高而不得不妥协"的窘境。

当然，Lütke 并非盲目乐观的"AI 吹"。他同样直言，大多数人之所以没发挥出 AI 的威力，是因为提示词（Prompt）给得"不够有野心"，还在用旧时代的任务拆解思维去限制模型 ；而一旦把 AI 真正当成需要长期练习的"乐器"来驾驭，掌握这种协作方式的人和固守旧习惯的人之间，生产力差距后面将跟着好几个零。

至于全球存量代码是否真会在 12 个月内被全部重写，时间表或许仍有讨论空间。但可以确定的是，那个靠给祖传老系统打补丁、在层层抽象里讨生活的时代，正在加速落幕。

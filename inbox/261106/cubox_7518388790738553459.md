> TL;DR：HarnessRouter 把 Codex、Claude Code、Hermes 等完整 Agent 运行时包装成统一的产品后端。产品提交任务和文件，选择 harness 与模型配置，收回进度、会话、产物和结构化失败。其价值主要是复用成熟 harness、减少产品化管道工程，并用 Unified Harness Protocol 降低迁移成本；创新在任务级契约与运行生命周期，而非新模型或新 Agent 算法。它适合把 Agent 能力嵌进产品的团队，对个人单 harness 编程并非必需。

## HarnessRouter 是什么？

HarnessRouter 是一层位于产品与 Agent 运行时之间的后端基础设施。它不自己发明一套规划循环，而是把 Codex、Claude Code、Hermes 等现成 harness 当作可替换的执行后端，在外面补齐产品需要的统一 API、会话、流式进度、文件、取消、错误和追踪。产品面对的是一次完整任务，而不是一次模型补全。

以合同审查功能为例，产品后端提交合同、审查指令和已配置的 harness；HarnessRouter 在隔离工作区启动相应 Agent，持续返回进度，最后交付风险清单、引用文件和执行轨迹。用户继续追问时，产品通过 response 和 session ID 回到原工作区。这个流程描述的是公开协议与文档规定的集成方式，不是本次部署实测。

因此，它的抽象单位不是"哪个模型回答 Prompt"，而是"哪套 Harness × Model 配置完成工作"。模型只是执行中的一项配置，指令、工具、技能、环境和运行限制也一起进入产品后端。

## 为什么有必要，优势落在哪里？

必要性来自一个容易被模型 API 掩盖的事实：demo 里的 Agent 循环与产品里的 Agent 后端之间，隔着大量不直接产生差异化、却必须可靠的工程。任务要能幂等提交，进度要能流式展示，断线后要找回结果，用户追问要恢复原工作区，取消要真正停止进程，生成的文件要能下载，多租户之间还要隔离凭证与数据。每接一种 harness 都重写这套适配，产品团队会持续追逐上游 CLI 和 SDK 的变化。

HarnessRouter 的选择不是再发明一个"更强的 Agent"，而是把 Codex、Claude Code、Hermes 等现成运行时当作黑盒后端。截至 2026 年 10 月 26 日，其开源 README 列出 26 种 harness base。产品保存的是一份配置：基础 harness、模型、指令、工具、技能、环境和限制；调用侧通过统一接口启动任务。这样既能复用头部厂商和开源社区已经投入的 harness 工程，也把"换一个后端"从产品改造缩小为配置与验证问题。

第二个优势是**可以比较 Harness × Model，而不是只比较模型** 。官方 Care Prep 测试在同一受控任务上比较八组配置，每组运行五次，报告成本从 0.47 到 223 credits、端到端延迟相差 3.2 倍；即使固定模型，更换 harness 也会改变成本和速度。这说明路由空间确实不止模型名。但这只是厂商发布的一项合成数据任务，质量门槛也针对该任务设计，不能外推成"所有工作负载便宜 99.8%"。Arena 当前的作用也是并行运行多组配置、让开发者选胜者，而不是证明自动路由已经普遍优于固定配置。

第三个优势是部署可迁移。Apache 2.0 Community Edition 将 Console、Gateway、Runner 放进一个 Docker 部署，状态存在本地 SQLite 和卷中；Cloud 则提供托管扩缩容与 serverless 隔离沙箱。同一 UHP 契约让团队可以本地开发、再迁移配置到云端。对需要自管文件和密钥的团队，这比只有托管 API 的封装服务更有吸引力。

## 技术上的创新，不在"路由"两个字里

其核心是 Unified Harness Protocol（UHP）。当前公开版本为 2026-10-19，仍是 draft standard，采用 OpenAPI 3.1 与 JSON Schema 描述，并附带 conformance suite。它把 harness 选择、任务、流式事件、会话、插件、环境、记忆、文件、取消、错误与安全放进同一个版本化契约。与 MCP 标准化工具有何不同？MCP 连接 Agent 与工具，UHP 连接产品与完整 Agent 运行时，二者不在同一边界。

UHP 有意复用 OpenAI Responses API 的请求形状和事件词汇，再在 metadata、附加字段和对象类型中扩展 harness 语义。这是一项务实的兼容性设计：已有 SDK、SSE 解析器和 UI 组件可以保留，新增能力又不会改变原字段含义。它还要求能力发现，允许扩展配置，试图避免统一 API 沦为所有后端最低能力的交集。不过，扩展越多，实际可移植性越依赖各实现是否一致支持，conformance 结果比"支持 UHP"的标签更重要。

更有工程价值的是生命周期语义。首个事件给出 response 与 session ID，事件带连续序号，流只能有一个终态；传输重试使用相同幂等键，断流后查询已存结果，而不是制造第二次执行；关闭 SSE 不等于取消任务。incomplete 与 failed 也被区分：预算耗尽可以保留部分工作并继续，取消则通过结构化状态表达。这些不是新算法，却是长任务基础设施与聊天封装之间的分水岭。

因此，"Router"不应被理解成已经解决了自动调度。团队早期 Show HN 讨论明确把 harness fallback、成本优化等 smart routing 列为路线图；当前 Arena 文档主要是并行比较，README 虽有 Auto 配置能力，也不足以证明生产流量已经能按任务自动选择最优后端。它今天最扎实的创新是**协议适配加任务控制面** ，智能路由仍是需要持续验证的上层能力。

## 和 OpenRouter 的区别

两者是类比关系，也是可以上下组合的技术关系。公开资料没有显示 HarnessRouter 是 OpenRouter 的产品或子项目。"OpenRouter for harnesses"只是前者用来解释定位的说法：OpenRouter 在多种模型和提供方之间统一接口，HarnessRouter 在多种 Agent 运行时之间统一接口。

OpenRouter 的核心 API 接收消息和模型名，返回文本、结构化数据或工具调用，解决模型目录、提供方选择、fallback 和统一计费；HarnessRouter 管理完整任务，返回文件、diff、产物、轨迹与终态。OpenRouter 也有能处理工具循环和状态的 Agent SDK，所以边界并非"只能聊天"，而是主要统一对象不同。只用 Agent SDK 自建 Agent 时不必增加 HarnessRouter；希望不重写产品后端就能更换 Codex 与 Claude Code 时，才对应后者的需求。OpenRouter 还可以作为底层模型访问层，但不是必需组件。

## 谁需要它，谁可以先不用？

最匹配的是把 Agent 作为产品功能交付的团队，例如合同审查、幻灯片生成、数据分析或代码修复服务。这类产品需要文件和状态，不只需要一个答案；也可能按任务类别选择不同 Harness × Model 组合。统一控制面能减少后端重复建设，并保留后端替换空间。

如果只是个人使用一个 coding agent、任务单一且上游接口稳定，直接围绕该 harness 的 SDK 或 app server 集成通常更简单。增加 HarnessRouter 也意味着新的控制面、适配损耗和运维对象。自托管版用每会话操作系统用户和工作区隔离，并非每会话独立容器；托管版虽宣称 serverless isolated sandbox，但公开资料没有披露其内部隔离实现。生成 HTML 和代码仍需在预览前隔离，产品自身也必须完成用户授权与所有权检查。它减少的是集成与运行管道成本，不会替产品承担全部安全责任，也不会自动带来更好的任务质量。

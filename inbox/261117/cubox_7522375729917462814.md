> TL;DR：LoopForge 把 Coding Agent 接进一条可暂停、返工和审批的研发流程。平台保存需求、运行状态与阶段产物，Worker 按依赖调度角色，角色再调用 CodeBuddy、Codex、DeepSeek Harness 等 CLI。开源稳定版 v0.3.8 的通用前端模板由六个 Agent 节点和一个人工验收节点串行组成，测试命令硬门禁需要另行配置。所谓「自进化」有明确的写回路径：用户发起运行评测，选中建议后更新 SOP 或角色，内置模板则生成项目草稿。

## 平台把什么交给 Agent

腾讯轻量云团队在 2026 年 11 月 9 日的发布文章里，把 LoopForge 描述为一套能在云端持续接单、按标准作业流程（SOP）推进交付的团队平台。公开仓库采用 MIT 许可证，包含自托管平台和 LoopForge Local。截至 11 月 14 日，GitHub 标记的最新稳定版是 11 月 12 日发布的 v0.3.8，本文以该标签为基线。公开仓库保留了执行引擎、持久化和 Runner 协议，团队的生产配置、私有系统接入和真实工单数据属于部署侧。   

对话入口和 SOP 处理的是两类工作。Main Bot 能打开项目工作区、修改代码、调用项目角色，按会话确认策略操作平台工具。进入 SOP 后，节点依赖、产物要求和失败路径由引擎执行。一个运行通常有自己的工作区，同次运行的节点共享其中的源码和分支。流程图可以分叉，依赖就绪的节点可以并行，同工作区里调用同一个角色的 CLI 会串行化。内置的通用前端模板恰好是一条线，因此该模板里的多个角色按顺序交接。   

默认部署用 Go 服务和 MySQL，执行侧使用 Docker，也可以接独立的执行机器。服务支持 api、worker 和 all 三种进程角色。API 可先持久化 Run，再由 Worker 认领和续租。每次运行记录流程和沙箱快照，执行结果提交时校验租约归属、运行代次与节点尝试次数，防止旧 Worker 覆盖新的运行状态。恢复仍受工作区所在机器与磁盘状态约束；Lease 并不能带回丢失的未提交文件。   

执行器是独立的一层。比如 Codex 适配器构造 codex exec --json 命令并解析 JSONL，平台把流式事件写进节点记录。公开版还注册了 Claude Code、DeepSeek Harness 等执行器，通用前端模板的六个角色起步配置都是 CodeBuddy。进入真实任务前，要分别确认对话使用的 CLI、各 SOP 角色使用的 CLI，以及执行环境有没有相应的凭据和工具。LoopForge Local 则把内置工作流安装进已有的编程助手，流程状态由本地脚本和宿主管理。v0.3.8 尚未支持将平台上自定义的 SOP 导出到 Local 独立运行。   

## 一条前端需求怎样走到验收


![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fmmbiz_png%2FTa2h2oOxYtJicmz1Jg6ANL7icUedBpUtWdpI01at5TJtvUPFeZpGfRibERQkr8uHicm67JlEhtggQdXLBTun8dPnKWaiaewGiay5sD9F8Xd9n6AFM%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D1)

图示为官方通用流程，其中「运行测试」画的是脚本节点。下面追踪公开版实际预置的通用前端模板，它的测试验证节点类型为 Agent。   

以「做一个短剧小程序」为例，需求确认和派发后，平台把需求、项目、责任人以及可选的仓库带进 Run。绑定仓库时可以检出源码和工作分支，新项目也可以从空工作区开始。节点按顺序定型需求、出设计、实现、独立评审、测试，等待人工验收后再汇总交付。前五步各有必需的 Markdown 产物，分别是 requirement.md、design.md、implementation.md、review.md 和 test-report.md，末尾生成 delivery.md。引擎把上游产物落到 .agentflow/inputs/，在节点提示里给出路径、摘要哈希和大小。后续角色可以读原文件，也能在同一工作区查看源码和 diff。   

「独立评审」指分开的角色与执行轮次，可以配置不同模型。该角色在同一个工作区读取实现结果，按提示把阻断问题写进 review.md。引擎推进流程看的是 MCP 工具 submit_gate_result 提交的结构化结果。它接受 pass、rework、fail、human 四种决定，rework 要有配置好的回退目标。预置前端模板把 rejectTo: implement 设在人工验收节点，评审节点本身没有这个目标。因此报告里的 REJECT 字样和引擎真的把任务退回实现，是两件需要分别检查的事。   

测试角色被要求跑项目真实命令，把退出码和未验证项写进测试报告。该模板的产物契约检查必需文件是否可读，命令门禁需要另行配置。配置后，引擎会在工作区自行执行命令并记录命令与失败输出。节点失败可按配置重试、打回或转人工。同次尝试内的自修正还需要开启角色的 Loop、配置相应失败策略和迭代上限。人工通过会写入 decision.md 并继续下游，打回开发会把实现及其后继节点重置为待执行，并把返工理由带给实现角色。   

交付节点可以汇总工作区源码和报告。预置角色提示只在用户明确要求、目标 GitHub 仓库和凭据齐备时创建 PR。判断是否合入时，应查看 GitHub 上对应 PR 的状态。这个版本的 SOP 成功路径也会更新平台工单的交付字段，即使没有关联 PR，因此平台自己的完成标记不能用来认定代码已合入。11 月 11 日的短剧案例记录了 SOP 走完、人工通过和产物可下载。作者当时只让 Agent 渲染了几张页面，微信开发者工具中的实际运行效果仍待验证。   

## 「自进化」怎么写回下一次运行


![](https://cubox.pro/c/filters:no_upscale()?imageUrl=https%3A%2F%2Fmmbiz.qpic.cn%2Fsz_mmbiz_png%2FTa2h2oOxYtJDjpwDOqsuzr7eNA5cZziacfJ7ibrZbVqaoSrDGTcTVhKFVO5H0NOO4ZxeodQd8BzXKpicDficPfL4QPswfCaCPs2avcWTKtibRPj0%2F640%3Fwx_fmt%3Dpng%26from%3Dappmsg%23imgIndex%3D2)

腾讯的发布文章用「工程级 RSI」描述两层反馈。运行中，脚本报错或评审结论能改变当次运行的走向。跨运行时，评测模型可以针对 SOP 和角色给出结构化修改建议。公开版 v0.3.8 的入口是运行详情中的「开始评测」。前端调用 POST /api/runs/:id/eval，后端只接受已成功、失败或取消的运行，还要求发起人有自己的 CodeBuddy API Key。源码的正常结束路径负责记录终态、标记交付与清理工作区，评测由独立入口触发。   

评测模型接收的是运行事实摘要，包含节点状态、尝试和返工次数、耗时、门禁事件、工具重复调用、Token 用量、错误和产物数量。程序校验模型给出的维度分，按项目权重计算 0--100 分。默认阈值是 70，控制流健康权重最高。这个分数描述流程运行情况，不能直接用来判断代码正确性。模型可建议修改节点重试或失败策略、追加角色提示词、增加或删除验证门禁。   

用户确认所选建议后，/api/runs/:id/eval/apply 才写入定义。可编辑的项目资产可以直接更新，针对内置 SOP 的修改写到项目草稿，针对共享角色的修改会复制角色并尝试更新项目流程里的引用。保存和发布是不同入口，历史运行仍保留当时的快照。从源码能确认的是「运行证据 → 评测建议 → 人工应用 → 更新团队流程」这条链。腾讯在发布文章里给出的分数变化是演示个例，缺少用来衡量后续任务是否普遍变好的公开对照数据。   

## 云端值守的条件

「7×24」依赖常驻的服务、可用的执行环境和凭据。公开版支持定时运行 Agent，也支持按触发配置扫描需求并派发 SOP。等待人工审批时，如果没有就绪或仍在运行的节点，运行进入 waiting，归还 Worker 租约。配置了集成分支的定时运行还可以串行合流，发现冲突时将任务打回修复节点。这里的自动化范围取决于项目的触发、审批和仓库设置。   

默认 Compose 安装把宿主的 Docker socket 挂给平台，官方将部署范围定位为可信团队。GitHub 设备授权申请 repo 权限，授权范围由 GitHub 账号可访问的仓库和组织策略决定。定时 Agent 沿用对话的完全权限策略，项目内的任务按项目 Owner 身份运行。对团队而言，LoopForge 把产物、失败重跑和批准记录留在同一次运行里。交付可信度取决于项目配置了哪些硬门禁，以及用什么身份执行和对外写入。   

本次在 v0.3.8 源码上构建了前端，并运行 12 个现有 Go 测试，覆盖控制面入队、租约代次保护、并行节点、门禁返工、评测准入与写回。评测 API 测试使用模拟模型结果。Docker 部署、真实模型调用和短剧案例的端到端交付未在本次运行。
